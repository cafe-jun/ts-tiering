# W5~W6 — 파티션 스킴 × granularity × 정렬

측정일: 2026-08-10 ~ 08-11
환경: macOS (darwin 23.4.0, Apple Silicon), Java 17, parquet-java 1.17.1,
DuckDB JDBC 1.3.1.0, MinIO `RELEASE.2025-09-07T16-13-09Z` (Docker, 루프백)
데이터: 30일 = 11,016,000행 (테넌트 3 × 디바이스 17 × 키 5, 60초 주기)
공통 설정: PER_KEY_TYPED + ZSTD, **행 그룹 64 KiB**, `--max-open-writers=512`

```
./gradlew :bench:ingest --args="--days=30 --devices-per-tenant=17 --interval-seconds=60 \
    --row-group-kib=64 --max-open-writers=512 --scheme=<스킴> --sort=<bool> \
    --writer-version=<v1|v2> --s3=true --s3-prefix=<라벨>"
./gradlew :bench:query --args="--prefixes=<라벨,...> --iterations=10 --warmup=2"
```

> **행 그룹 64 KiB 는 인위적인 값이다.** 운영에서는 128 MB 를 쓴다. 그런데 이 데이터셋의
> 파일이 10~500 KiB 라 현실적인 행 그룹 크기를 쓰면 **파일당 행 그룹이 1개**가 되고,
> 그러면 정렬 순서 축을 측정하는 것 자체가 불가능하다. 64 KiB 는 그 축을 열기 위한 장치이며,
> 이 때문에 절대 크기가 [W3](w3-s3-ingest.md)(행 그룹 32 MiB)보다 약 4배 크다.
> 스킴 간 비교는 같은 조건이므로 유효하다.

## 세 축을 분리한다

계획서는 "경로에 무엇을 넣을지"만 변수로 뒀지만, W3 에서 시간 축 granularity 가 더 큰 변수임이
드러났다. 여기서는 세 축을 분리한다.

| 축 | 값 |
|---|---|
| **스킴** (경로 구성) | A `date` / B `tenant/profile/date` / C `tenant/device/date` |
| **granularity** (시간 세분화) | `date` / `date+hour` |
| **파일 내 정렬** | 도착 순서(ts) / `(device_id, ts)` |

여기에 측정 도중 네 번째 축이 필요해졌다 — **Parquet 라이터 버전(v1/v2)**. 이유는 아래에.

## 읽어낸 것

### 1. 스킴 C 는 바이트를 26배 줄이고 지연을 43배 늘린다

Q1 에서 C 는 1,530개 중 7개만 열고 **0.08 MiB** 만 전송한다. A 의 2.10 MiB 대비 26배 적다.
디바이스를 경로에 넣으면 프루닝이 완벽하게 걸린다는 뜻이고, 계획서의 예상대로다.

그런데 **p50 은 1,171ms 로 A 의 27ms 보다 43배 느리다.** 그 중 540ms — 절반 가까이가
객체 나열이다. 바이트를 아무리 줄여도 1,530개 객체를 나열하는 비용이 남는다.

**프루닝의 승자와 지연의 승자가 정반대다.** 이게 이번 측정의 핵심이다.

### 2. 넓은 질의에서는 C 가 바이트로도 최악이다

Q3(프로파일 전체)에서 C 는 **15.80 MiB** 를 전송한다. A(6.50)의 2.4배다.
1,530개 파일을 전부 읽어야 하는데 파일마다 푸터·딕셔너리 페이지가 붙기 때문이다.

즉 C 의 이점은 **디바이스를 지정하는 질의에만** 있고, 그 외에는 용량·지연 모두 손해다.

### 3. granularity 를 시 단위로 내리는 것은 순수 손해다

| | 파일 수 | Q1 전송 | Q1 p50 |
|---|---|---|---|
| A-date | 30 | 2.10 MiB | 27ms |
| A-hour | 720 | 2.40 MiB | 371ms |
| B-date | 90 | 0.76 MiB | 42ms |
| B-hour | 2,160 | 0.84 MiB | 1,215ms |

바이트도 늘고 지연은 14~29배 늘어난다. 얻는 게 없다 — 질의가 시 단위로 좁혀지지 않는 한
hour 파티션은 프루닝에 기여하지 못하면서 파일만 24배로 쪼갠다.
[W3 의 크기 측정](w3-partition-granularity.md)에 이어 쿼리 쪽에서도 같은 결론이다.

### 4. 정렬은 전송 바이트를 절반으로 줄인다

`(device_id, ts)` 정렬로 행 그룹의 `device_id` min/max 가 좁아져 행 그룹 프루닝이 걸린다.

| | Q1 전송 | Q2 전송 | 행 그룹 프루닝 |
|---|---|---|---|
| A-date → A-date-sorted | 2.10 → **1.00** (−52%) | 8.30 → **3.60** (−57%) | 0% → **97.7%** |
| B-date → B-date-sorted | 0.76 → **0.45** (−41%) | 2.60 → **1.50** (−42%) | 0% → **93.1%** |

푸터 통계 기반 시뮬레이션(0% → 97.7%)이 실제 전송 바이트(−52%)로 확인됐다.
시뮬레이션과 실측이 서로를 검증한다.

**스킴 C 에는 이 축이 없다.** 파일 하나가 디바이스 하나라 정렬해도 순서가 바뀌지 않는다 —
`C-date` 와 `C-date-sorted` 가 바이트 단위로 동일하다(77,820,983 both).

### 5. 정렬의 저장 대가는 Parquet v1 의 한계였다

정렬을 켜자 총 크기가 43.0 → **66.8 MiB (1.55배)** 로 뛰었다. 열별로 뜯어보니 원인이 `ts` 였다.

| | `ts` 압축전 → 압축후 | 인코딩 |
|---|---|---|
| A-date (도착순서, v1) | 21K → 20K | `PLAIN_DICTIONARY` |
| A-date-sorted (v1) | 577K → **210K** | **`PLAIN`** (폴백) |
| A-date-sorted-v2 | 30K → **10K** | **`DELTA_BINARY_PACKED`** |

도착 순서에서는 행 그룹(64 KiB ≈ 566행) 안에 고유 ts 가 11개뿐이라 딕셔너리가 거의 공짜다.
정렬하면 같은 행 그룹에 566개의 고유 ts 가 들어가 딕셔너리가 이득을 잃고 `PLAIN`(8바이트/행)으로 떨어진다.
`device_id` 에서 아낀 35K 보다 `ts` 에서 잃은 190K 가 훨씬 크다.

**Parquet v2 를 켜면 뒤집힌다.** 오름차순 정수에 `DELTA_BINARY_PACKED` 가 붙는다.

| | 도착 순서 | 정렬 |
|---|---|---|
| v1 | 43.0 MiB | 66.8 MiB (**+55%**) |
| v2 | 43.4 MiB | **37.9 MiB** (**−12%**) |

즉 **정렬 + v2 는 저장 용량을 줄이면서 전송 바이트도 절반으로 줄이는 순수 이득**이다.
쿼리 성능은 v1 정렬본과 동일하다(Q1 0.97 vs 1.00 MiB, p50 둘 다 22ms).

라이터는 `ParquetWriter.DEFAULT_WRITER_VERSION`(= `PARQUET_1_0`)을 쓰고 있었다.
이 기본값이 정렬의 이점을 통째로 가리고 있었던 셈이다.

### 6. 스킴 B 의 `profile=` 계층은 아무 일도 하지 않는다

DuckDB 에 컬럼 목록을 물어보면 스킴 B 는 `tenant` 만 추가로 노출하고 `profile` 은 하나뿐이다.
Parquet 파일 안에 같은 이름의 `profile` 열이 있어서(ADR-0002 의 스키마) **파일 열이 경로
파티션을 가린다.** W4 의 `EXPLAIN` 에서 File Filters 에 `date` 와 `tenant` 만 있고
`profile` 이 없던 것도 이것 때문이다.

경로가 한 단계 길어지는 비용만 내고 프루닝 이득은 0이다.
Hive/Iceberg 가 파티션 열을 파일에 중복 저장하지 않는 이유가 여기 있다.

## 채택안 검증

ADR-0004 가 고른 조합(`tenant/date` + 정렬 + v2)을 실제로 적재해
계획서의 원래 스킴 B(`tenant/profile/date` + 도착순서 + v1)와 비교했다.

| | B-date | **DEFAULT** | 차이 |
|---|---|---|---|
| 저장 크기 | 43.8 MiB | **38.0 MiB** | **−13.2%** |
| 평균 파일 | 112.0 KiB | 99.4 KiB | |
| Q1 전송 | 0.76 MiB | **0.42 MiB** | **−44.7%** |
| Q2 전송 | 2.60 MiB | **1.50 MiB** | **−42.3%** |
| Q3 전송 | 7.10 MiB | 7.60 MiB | +7.0% |
| Q1 p50 | 42ms | 42ms | ±0 |
| Q2 p50 | 55ms | **46ms** | −16.4% |
| Q3 p50 | 80ms | 92ms | +15.0% |
| 나열 | 16ms | 16ms | ±0 |

세 축(`profile` 제거 / 정렬 / v2)을 한꺼번에 바꾼 비교다.

**좁은 질의는 크게 좋아지고 넓은 질의는 조금 나빠진다.** Q3 는 모든 파일을 읽으므로
프루닝의 이득이 없는데, v2 의 데이터 페이지 구조 차이로 7% 더 읽는다.
전체 저장 용량은 13% 작은데도 Q3 전송이 늘어나는 건 설명하지 못한 부분이다 —
페이지 단위 읽기 패턴 차이로 보이나 확인하지 않았다. 규모가 작아 추적하지 않고 기록만 남긴다.

cold 계층의 접근 패턴은 "가끔, 좁게"에 가까우므로 이 교환은 받아들일 만하다.

## 이 결과의 한계

**나열 비용이 결론을 지배하는데, 그건 이 규모의 성질이다.** 파일이 10~500 KiB 라
객체 수가 지연을 좌우한다. 파일이 100 MB 급이면 바이트가 지배하고 순위가 뒤집힐 수 있다.

**카탈로그가 있으면 순위가 뒤집힌다 — 단 조건이 있다.** 처음에는 "나열이 사라지면
C 가 최선"이라고 적었는데, [실제로 재보니](w6-manifest-vs-glob.md) 나열 제거만으로는
부족했다. 카탈로그가 **파티션 통계로 걸러서** 넘겨야 C 의 Q1 이 6ms 가 되고 그때 최선이 된다.
목록만 넘기면 84ms 로, 같은 조건의 B(15ms)보다 여전히 느리다.

**MinIO 루프백이다.** 실 S3 는 LIST 왕복이 더 비쌀 것으로 보이나 **미검증 가정이다.**
AWS 는 이 프로젝트의 범위 밖이다.

**단일 프로세스, 동시성 없음.** 대시보드가 초당 수백 번 읽는 상황은 재지 않았다.
