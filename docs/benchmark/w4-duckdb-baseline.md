## 쿼리 3종

PHASE1.md 가 정한 형태다. **W5~W6 에서 스킴을 바꿔도 이 본문은 고정한다** — 경로만 바뀌어야 비교가 성립한다.

| | 내용 | 반환 행 |
|---|---|---|
| Q1 | 단일 디바이스 / 단일 키 / 7일 | 10,080 |
| Q2 | 단일 디바이스 / 단일 키 / 1년 일평균 | 365 |
| Q3 | 프로파일 전체 / 단일 키 / 1개월 평균 | 1 |

### 키는 WHERE 가 아니라 경로에 넣어야 한다

처음에는 `WHERE key = 'temperature'` 로 썼는데 `avg(value)` 가 바인딩 에러를 냈다.

```
Binder Error: No function matches the given name and argument types 'avg(VARCHAR)'
```

PER_KEY_TYPED(ADR-0002)에서 `value` 의 **물리 타입이 키마다 다르기 때문**이다 —
`temperature` 는 DOUBLE, `running` 은 BOOLEAN, `error_code` 는 VARCHAR.
키를 가로지르는 glob 을 주면 DuckDB 가 스키마를 통합하면서 `value` 를 VARCHAR 로 내려버린다.

그래서 키를 glob 경로에 박았다.

```sql
read_parquet('s3://…/tenant-profile-date/**/key=temperature/*.parquet', hive_partitioning = 1)
```

**이건 ADR-0002 의 숨은 대가다.** 압축률 비교에서는 드러나지 않았고 쿼리 시점에 나타났다.
실제 쿼리 라우터도 키를 알고 들어오므로 실용상 문제는 아니지만,
"아무 키나 한 번에 훑는" 질의는 캐스팅 없이는 불가능하다는 뜻이다.

## 읽어낸 것

### 1. 파티션 프루닝은 확실히 걸린다

`EXPLAIN ANALYZE` 가 직접 보여준다.

```
File Filters: (date BETWEEN '2026-03-01'::DATE AND '2026-03-08'::DATE)
              (tenant = '00000000-007e-4a47-0000-000000000000')
Scanning Files: 7/1095
```

`tenant` 과 `date` 는 **파일 필터**로 밀려 내려가 1,095개 중 7개만 연다.
`device_id` 는 파일 안의 열이라 행 필터로 남는다 — 스킴 B 의 구조가 그대로 드러난다.
스킴 C(`tenant/device/date`)로 바꾸면 `device_id` 도 파일 필터가 될 텐데, 그게 W5~W6 의 비교 지점이다.

### 2. 그런데 프루닝이 지연으로 이어지지 않는다

**스캔량은 52배 차이(0.22 → 11.50 MiB)인데 p50 은 1,085ms 와 1,136ms 로 5% 차이다.**

이유는 표의 마지막 줄에 있다. **531ms — 지연의 절반이 바이트를 한 개도 읽기 전에, 객체를 나열하는 데 든다.**
`**/key=temperature/*.parquet` 을 풀려면 프리픽스 트리 전체를 LIST 해야 하고,
프루닝은 그 목록이 나온 다음에야 적용된다.

읽는 비용 자체는 싸다. Q2 는 Q1 보다 358개 파일을 더 읽는데 51ms 밖에 더 안 걸린다 —
**파일당 0.14ms**. 즉 이 데이터셋에서 지연은 거의 전부 고정비다.

이건 W3 의 업로드 결과와 정확히 같은 이야기다. 그때는 132 MiB 를 올리는 데
객체당 4.4ms × 5,475번이 들었고, 지금은 읽는 쪽에서 같은 일이 벌어진다.
**small file 환경에서 비용은 바이트가 아니라 객체 수에 붙는다.**

### 3. Q2 만 p95 가 튄다

p50 1,136ms / p95 2,450ms 로 2.2배다. Q1(1.11배)·Q3(1.04배)과 다르다.
365개 파일을 여는 쪽이 편차가 크다 — 열어야 할 파일이 많을수록 꼬리가 길어진다.
평균만 보면 안 되는 지점이다.

### 4. W5~W6 의 측정 지표를 바꿔야 한다

계획서는 스킴 비교의 지표로 "쿼리 p50/p95"와 "스캔 바이트"를 나란히 뒀다.
그런데 이 데이터셋에서 **p50/p95 는 스킴을 구분하지 못한다** — 531ms 의 나열 비용이 모든 차이를 덮는다.

의미 있는 지표는 **스캔 파일 수 / 프루닝 비율**이다. 이건 `EXPLAIN ANALYZE` 에서 정확히 나오고
스킴에 따라 확실히 달라진다. 하네스가 자동으로 뽑도록 해뒀다.

한 가지 더 — **스킴 C 는 나열 비용이 더 나빠질 것이다.** 디렉터리가 디바이스 수만큼 늘어나
LIST 해야 할 프리픽스가 많아진다. 프루닝은 좋아지고 나열은 나빠지는 상충이라,
W5~W6 은 이 둘을 함께 봐야 한다.

## 이 숫자의 한계

- **MinIO 루프백이다.** 실 S3 는 LIST 왕복이 훨씬 비싸므로 나열 비용의 비중이 더 커질 것으로
  보이지만, **이건 미검증 가정이다.** AWS 가 이 프로젝트의 범위 밖이라 확인하지 못했다
- **연결 하나를 재사용한다.** DuckDB 가 Parquet 푸터와 HTTP 메타데이터를 캐시하므로
  p50/p95 는 warm 수치다. cold 는 별도 열에 뒀다
- **단일 프로세스, 동시성 없음.** 대시보드가 초당 수백 번 읽는 상황은 재지 않았다

## 곁가지: 운영에서의 함의

나열이 지배한다는 건 곧 **LIST 를 없애야 한다**는 뜻이다. 방법은 둘이다.

1. **파일을 크고 적게** — 현재 32.3 KiB 짜리 1,095개. compaction 이 Phase 3 에 있는 이유다
2. **매니페스트를 두기** — Iceberg / Delta / Glue 카탈로그가 존재하는 이유가 정확히 이것이다.
   파일 목록을 메타데이터로 들고 있으면 LIST 가 사라진다

Phase 1 범위 밖이지만, 이 측정이 그 필요성을 숫자로 보여준다.
