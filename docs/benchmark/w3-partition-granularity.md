# W3 프로브 — 파티션 granularity 와 small file

측정일: 2026-08-09
환경: macOS (darwin 23.4.0, Apple Silicon), Java 17, parquet-java 1.17.1
데이터: A안 구성의 30일치 = 11,016,000 건 (테넌트 3 × 디바이스 17 × 키 5, 60초 주기)
레이아웃/코덱: PER_KEY_TYPED + ZSTD (ADR-0002)

```
./gradlew :bench:ingest --args="--days=30 --devices-per-tenant=17 --interval-seconds=60 --scheme=tenant-profile-date-hour"
./gradlew :bench:ingest --args="--days=30 --devices-per-tenant=17 --interval-seconds=60 --scheme=tenant-profile-date"
```

## 왜 이걸 먼저 쟀나

1억 건 적재(W3 본 측정)에 들어가기 전에 파티션 경로를 하나 정해야 했다.
계획서의 스킴 B 는 `tenant/profile/date/hour` 인데, A안 데이터셋에 대입해보니
시(hour) 파티션 하나에 들어가는 행이 **테넌트당 17 디바이스 × 60틱 = 1,020 행**밖에 안 됐다.
Parquet 파일 하나에 천 행이면 푸터와 딕셔너리 페이지가 데이터보다 클 수 있다.
본 측정을 돌리기 전에 확인할 값어치가 있었다.

## 결과

| granularity | 파티션 수 | 파일 수 | 평균 파일 | 총 크기 | 건당 | NDJSON 대비 | 적재 |
|---|---|---|---|---|---|---|---|
| `date/hour` | 10,800 | 10,800 | **2.9 KiB** | 30.5 MiB | 2.90 B | 67.8x | 978,666 pt/s |
| `date` | 450 | 450 | **24.5 KiB** | **10.8 MiB** | **1.02 B** | **192.3x** | 1,176,574 pt/s |

같은 데이터, 같은 레이아웃, 같은 코덱인데 **시 단위로 쪼갠 쪽이 2.83배 크다.**

## 파일당 고정 오버헤드는 약 2.0 KB

두 측정의 차이가 전부 파일 수에서 온다는 점을 이용하면 오버헤드를 직접 뽑을 수 있다.

```
(31,958,328 − 11,272,888) bytes ÷ (10,800 − 450) files = 1,999 bytes/file
```

시 단위 파일이 평균 2.9 KiB 이므로 **전체 30.5 MiB 중 약 20.6 MiB (67.5%)가 오버헤드**다.
데이터가 아니라 푸터·딕셔너리 페이지·열별 메타데이터를 저장하려고 S3 에 올리는 셈이 된다.
(일 단위에서는 같은 계산이 899 KB / 10.8 MiB = 8.0% 로 떨어진다.)

W2 에서 이미 조짐이 있었다 — 값이 하나뿐인 `profile` 열은 압축하면 오히려 커졌다(14K → 18K).
그때 "파일을 잘게 쪼개면 파일마다 이 오버헤드가 붙는다"고 적어둔 것이 그대로 나타났다.

## 1년으로 외삽

하루 안의 특성이 매일 반복되므로 30일 측정은 그대로 확장된다.

| granularity | 1년 파일 수 | 예상 총 크기 | 그 중 오버헤드 |
|---|---|---|---|
| `date/hour` | 131,400 | 약 371 MiB | 약 250 MiB (67.5%) |
| `date` | 5,475 | 약 131 MiB | 약 10.4 MiB (8.0%) |

## 읽어낸 것

**1. small file 의 지배 변수는 스킴이 아니라 granularity 였다.**
계획서는 W5~W6 에서 스킴 A/B/C(경로에 무엇을 넣을지)를 비교하도록 짜여 있는데,
정작 크기를 2.8배 흔든 것은 경로 구성이 아니라 시간 축을 얼마나 잘게 쪼개느냐였다.
**ADR-0003 은 스킴과 granularity 를 별개 축으로 다뤄야 한다.**

**2. W2 의 338배는 역시 부풀려진 값이었다.** 같은 레이아웃·코덱으로
현실적인 커버 기간(60초 주기, 하루 단위 파티션)에서 재니 **192배**가 나온다.
`ts` 고유값이 하루치 1,440개로 늘면서 딕셔너리 이득이 줄어든 것이 주된 차이다.
다만 192배도 여전히 NDJSON 대비이고, NDJSON 은 정직한 분모가 아니다 — Cassandra 대비는 별도 산출한다.

**3. 목표 파일 크기 128 MiB 는 이 데이터셋에서 작동하지 않는다.**
두 측정 모두 롤오버가 0이다. 1년치 **전체**가 date 단위에서 131 MiB 이므로,
128 MiB 짜리 파일 하나를 만들려면 1년을 통째로 한 파일에 넣어야 한다.
즉 **A안 데이터셋은 "적당한 크기의 Parquet 파일"을 만들 만큼 크지 않다.**
파일 크기 롤링은 코드로 준비돼 있지만 이 규모에서는 재는 대상이 아니다 —
디바이스를 늘리지 않는 한 W5~W6 에서도 마찬가지다.

**4. 라이터 축출은 무해했다.** 시 단위에서 축출이 10,736회 일어났는데 재개봉은 0이다.
생성기가 ts 오름차순이라 닫힌 시간 파티션에 데이터가 다시 오지 않는다.
축출 횟수가 아니라 **재개봉 횟수**가 small file 지표다 (`Stats.reopens()`).
단, 스킴 C(`tenant/device/date`)는 같은 시각에 모든 디바이스 파티션이 열려 있으므로
이 성질이 성립하지 않는다 — 거기서는 라이터 상한이 곧 파일 파편화가 된다.

## W3 본 측정에 반영할 것

- 기준 경로는 `tenant/profile/date` (시 단위 제외)
- `--max-open-writers` 는 재개봉 0을 유지하는 값으로. 스킴 C 는 디바이스 × 키 = 255 이상 필요
- 결과표에 `partitions / files / reopens` 를 함께 싣는다. 파일 수만으로는 원인이 안 보인다
