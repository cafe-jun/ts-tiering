# W6 보강 — 매니페스트가 있으면 스킴 순위가 뒤집히는가

측정일: 2026-08-11
환경: [W5~W6](w5-partition-schemes.md) 과 동일 (30일 / 11,016,000행 / DuckDB JDBC 1.3.1.0 / MinIO)

```
./gradlew :bench:query --args="--prefixes=A-date,B-date,C-date --iterations=10 --manifest=off"
./gradlew :bench:query --args="--prefixes=A-date,B-date,C-date --iterations=10 --manifest=full"
./gradlew :bench:query --args="--prefixes=A-date,B-date,C-date --iterations=10 --manifest=pruned"
```

## 왜 쟀나

[ADR-0004](../adr/0004-partition-scheme.md) 는 스킴 C(`tenant/device/date`)를 기각하면서
이렇게 적었다.

> 매니페스트 카탈로그를 도입하면 540ms 나열이 사라지고 "26배 적은 바이트"만 남아 C 가 최선이 된다.

**이건 측정이 아니라 주장이었다.** 그런데 AWS 없이도 확인할 수 있다 —
DuckDB 의 `read_parquet` 은 glob 대신 파일 경로 목록을 직접 받는다.
목록을 미리 만들어 넘기면 S3 를 나열하지 않으므로, 그게 카탈로그가 하는 일이다.

## 세 가지 소스 해석 방식

| 모드 | 무엇을 흉내내나 | 나열 | 프루닝 |
|---|---|---|---|
| `off` | 현행. glob 을 S3 에 풀어 목록을 얻는다 | **S3 LIST** | 엔진이 경로에서 |
| `full` | 카탈로그가 파일 목록만 준다 | 없음 | 엔진이 경로에서 |
| `pruned` | 카탈로그가 파티션 통계로 걸러서 준다 (Iceberg) | 없음 | **카탈로그가** |

`full` 과 `pruned` 를 나눈 것이 이 측정의 핵심이다.
목록만 넘기면 나열은 사라지지만 **경로 N개를 파싱하고 술어를 평가하는 비용**이 남는다.
실제 Iceberg 는 매니페스트의 파티션 통계로 그 단계까지 처리한다.

## 결과 (p50)

| 모드 | | Q1 | Q2 | Q3 |
|---|---|---|---|---|
| **`off`** (glob) | A-date | 28ms | 85ms | **56ms** |
| | B-date | 48ms | 56ms | 80ms |
| | C-date | **1,092ms** | 1,176ms | 1,324ms |
| **`full`** | A-date | 21ms | 66ms | 63ms |
| | B-date | 15ms | 35ms | 77ms |
| | C-date | 84ms | 80ms | 1,663ms |
| **`pruned`** | A-date | 21ms | 69ms | 59ms |
| | B-date | 10ms | 31ms | 87ms |
| | C-date | **6ms** | **15ms** | 1,866ms |

정확성 검증: 세 모드가 같은 행 수와 같은 전송 바이트를 낸다.
C-date 기준 Q1 10,080행 / 7 GET, Q2 30행 / 30 GET, Q3 1행 / 1,530 GET —
프루닝 모드에서 목록이 1,530 → 7 로 줄어도 결과가 같다.

## 읽어낸 것

### 1. ADR-0004 의 주장은 절반만 맞았다

**나열을 없애는 것만으로는 부족하다.** `full` 모드에서 C 의 Q1 은 1,092 → 84ms 로
13배 빨라지지만, 같은 조건의 B(15ms)보다 여전히 5.6배 느리다.
바이트는 9.5배 적게 읽는데도 그렇다. 남은 비용은 **경로 1,530개를 훑는 것**이다.

**카탈로그가 프루닝까지 해야 뒤집힌다.** `pruned` 모드에서 C 의 Q1 은 **6ms** 로
glob 대비 **182배** 빨라지고, 처음으로 모든 스킴 중 가장 빠르다 (B 10ms, A 21ms).
Q2 도 마찬가지다 (15ms vs B 31ms, A 69ms).

ADR-0004 가 지목한 메커니즘("나열이 사라진다")은 틀렸고,
결론("C 가 최선이 된다")은 맞았다. **조건이 더 강했던 것이다** —
파일 목록을 주는 카탈로그가 아니라 파티션 통계로 걸러주는 카탈로그여야 한다.

### 2. 넓은 질의에서 C 는 카탈로그가 있어도 최악이고, 오히려 나빠진다

Q3 는 1,530개 파일을 전부 읽어야 해서 프루닝할 것이 없다.
그런데 C 의 Q3 는 1,324 → 1,663 → **1,866ms** 로 모드가 진행될수록 느려진다.
목록을 넘기는 방식 자체의 비용(거대한 SQL 리터럴 파싱)이 나열 절감분보다 크기 때문이다.

같은 질의에서 A 는 59ms 다. **31배 차이가 카탈로그로 해소되지 않는다.**
이건 나열 문제가 아니라 파일 7,650개라는 형상의 문제다.

### 3. 카탈로그는 모든 스킴에 이롭지만 이득의 크기가 다르다

| Q1 개선 (glob → pruned) | |
|---|---|
| A-date (30 파일) | 28 → 21ms (1.3배) |
| B-date (90 파일) | 48 → 10ms (4.8배) |
| C-date (1,530 파일) | 1,092 → 6ms (**182배**) |

**파일이 많을수록 카탈로그의 값어치가 크다.** 뒤집어 말하면, 파일이 적은 스킴은
카탈로그가 없어도 손해가 작다 — 카탈로그 도입 전이라면 그게 곧 A/B 를 고르는 이유다.

## 이 측정이 답하지 못하는 것

**Athena 대체가 아니다.** 여전히 로컬 단일 노드이고, 관리형 엔진의 분산 실행·
과금 모델·콜드 스타트는 재지 않았다. Phase 1 종료 조건 3번의 "DuckDB vs Athena"는
**미검증으로 남는다.**

**실제 카탈로그를 쓴 것이 아니다.** Iceberg 매니페스트를 읽은 게 아니라 파일 목록을
SQL 에 박아 넣었다. 실제 카탈로그는 매니페스트 파일을 읽는 비용이 따로 있고,
그 비용은 여기 포함되지 않았다. 즉 `pruned` 는 **낙관적 상한**이다.

**측정 편차가 있다.** 같은 glob 모드를 두 번 재면 A-date Q1 이 27ms 와 28ms,
C-date Q1 이 1,171ms 와 1,092ms 로 나온다. 30% 안쪽 차이는 의미를 두지 말 것.
위에서 결론으로 삼은 것은 182배·31배처럼 편차를 한참 넘는 값들이다.
