# W3 — 1년치 S3 적재

측정일: 2026-08-09
환경: macOS (darwin 23.4.0, Apple Silicon), Java 17, parquet-java 1.17.1,
MinIO `RELEASE.2025-09-07T16-13-09Z` (Docker, 루프백)
데이터: A안 = 134,028,000 건 / 365일 커버 (테넌트 3 × 디바이스 17 × 키 5, 60초 주기)
레이아웃/코덱: PER_KEY_TYPED + ZSTD (ADR-0002)
파티션: `tenant=/profile=/date=` (근거는 [granularity 프로브](w3-partition-granularity.md))

```
docker compose -f deploy/docker-compose.dev.yml up -d
./gradlew :bench:ingest --args="--days=365 --devices-per-tenant=17 --interval-seconds=60 \
    --scheme=tenant-profile-date --s3=true"
```

> **LocalStack 이 아니라 MinIO 다.** 계획서는 LocalStack 을 전제했지만 커뮤니티 이미지가
> 2026-03 릴리스로 단종됐다 — `:s3-latest` 는 기동 시 "no longer available" 로 죽고,
> 통합 이미지는 `LOCALSTACK_AUTH_TOKEN` 없이 exit 55 로 끝난다.
> MinIO 는 S3 API 호환이고 multipart 도 지원하므로 재는 대상은 바뀌지 않는다.

## 읽어낸 것

**1. 업로드 시간은 바이트가 아니라 객체 수가 지배한다.**
132 MiB 를 올리는 데 24.1초, 5.5 MiB/s 다. 루프백 치고 형편없는 수치인데
객체당으로 보면 4.4 ms 로 일정하다. 즉 이 시간은 전송이 아니라 **요청 왕복 5,475번**이다.
파티션을 잘게 쪼개는 대가가 저장 용량(오버헤드 8.1%)뿐 아니라
적재 시간에도 그대로 나타난다.

**2. multipart 는 이 규모에서 한 번도 타지 않았다.**
가장 큰 파일이 임계값 8 MiB 에 한참 못 미친다. 코드와 통합 테스트
(12 MiB → 3파트)는 갖춰뒀지만 **A안 데이터셋에서 multipart 는 측정 대상이 아니다.**
"파일 크기별 업로드 시간"이라는 W3 항목은 이 데이터셋으로는 답이 나오지 않는다 —
파일 크기 분포가 24.7 KiB 한 점에 몰려 있기 때문이다. 답하려면 디바이스를 늘려야 한다.

**3. 축출 5,411회, 재개봉 0회.** 라이터 상한(64)에 계속 걸렸지만 파일은 하나도 더 늘지 않았다.
생성기가 ts 오름차순이라 닫힌 날짜 파티션에 데이터가 다시 오지 않는다.
파일 수(5,475)가 파티션 수와 정확히 같은 것이 그 증거다.
**축출 횟수는 small file 지표가 아니다 — 재개봉이 지표다.**
단 스킴 C(`tenant/device/date`)에서는 같은 시각에 모든 디바이스 파티션이 열려 있어
이 성질이 깨진다. W5~W6 에서 `--max-open-writers` 를 디바이스×키(255) 이상으로 둬야 공정해진다.

**4. 30일 프로브가 1년으로 그대로 확장됐다.** 프로브 예측 131 MiB / 실측 132.0 MiB,
압축비 192.3x / 190.6x. 하루 안의 특성이 매일 반복되므로 앞으로 W5~W6 비교는
30일 데이터셋으로 돌려도 된다 — 1년 실행 3분이 30일 20초가 된다.

## 아직 정직한 숫자가 아니다

**190.6배는 여전히 NDJSON 대비다.** W1·W2 문서가 반복해서 지적한 그 분모다 —
필드명과 UUID(36자)를 매 행 텍스트로 반복하는, 아무도 실제로 쓰지 않는 포맷.
W2 의 338배가 190배로 내려온 것은 커버 기간을 현실화한 결과이지
분모가 정직해진 결과가 아니다.

보고용 문장에 쓸 숫자는 **Cassandra 실제 디스크 대비**여야 한다. 아직 없다.
이 문서는 그 값이 나오면 갱신한다.
