# Phase 2 W1 — 지연 도착과 파티션 닫기

측정일: 2026-08-15
환경: macOS (darwin 23.4.0, Apple Silicon), Java 17, parquet-java 1.17.1
데이터: 30일 = 11,016,000행 (테넌트 3 × 디바이스 17 × 키 5, 60초 주기)
설정: `tenant=/date=/key=`, PER_KEY_TYPED + ZSTD, `(device_id, ts)` 정렬, Parquet v2 (ADR-0004)
지연: 비율 5%, 지수분포 평균 3일 / 상한 10일

```
./gradlew :bench:ingest --args="--days=30 --devices-per-tenant=17 --interval-seconds=60 \
    --scheme=tenant-date --sort=true --late-ratio=0.05 --late-mean-ticks=4320 --late-max-ticks=14400 \
    --close-policy=<lru|watermark-close|watermark-drop> --close-lag-minutes=N --max-open-writers=M"
```

## 왜 이걸 먼저 쟀나

Phase 1 의 결과는 **합성 생성기가 ts 오름차순으로 방출한다는 성질** 위에 서 있었다.
축출이 5,411회 일어나도 재개봉이 0이었고 파일 수가 파티션 수와 정확히 같았다
([W3](w3-s3-ingest.md)). Kafka 는 그렇지 않다.

그래서 Kafka 연동보다 이것을 먼저 뒀다. 순서를 바꾸면 나중에 라이터를 다시 쓰게 된다.

## 전제가 실제로 깨진다

지연 5% 를 주입하고 Phase 1 의 라이터를 그대로 돌렸다.

| 라이터 슬롯 | 파일 수 | 재개봉 | 총 크기 | 건당 | NDJSON 대비 |
|---|---|---|---|---|---|
| (지연 없음) | 450 | 0 | 11.2 MiB | 1.07 B | 184x |
| 64 | **203,449** | 202,999 | 345.6 MiB | 32.90 B | 6.0x |
| 16 | **1,019,755** | 1,019,305 | 1,708 MiB | 162.59 B | **1.2x** |

슬롯 16 에서 Parquet 은 NDJSON 보다 1.2배 작을 뿐이다 — **압축 이점이 사실상 전멸한다.**
평균 파일이 1.7 KiB 인데 이건 [W3 에서 잰 파일당 고정 오버헤드(약 2.0 KB)](w3-partition-granularity.md)보다도
작다. 저장하는 게 데이터가 아니라 푸터다.

**원인은 라이터에 닫기 정책이 없다는 것이었다.** 파티션은 LRU 축출·크기 롤링·최종 close 로만
닫혔고, 그래서 `maxOpenWriters ÷ 동시 파티션 수` 가 **우연한 유예 기간**으로 작동하고 있었다
(슬롯 64 / 일당 15 → 약 4.3일). 지연이 그 창을 넘으면 재개봉이 터지고,
450개 파티션을 64칸에 밀어넣으려니 스래싱이 된다.

## 전략 비교

닫기 정책 세 가지를 `ClosePolicy` 로 구현했다. 워터마크는 **이벤트 시각 기준**이다 —
슬롯마다 마지막 ts 를 기억하고 전역 최대 ts 보다 `lag` 이상 뒤처지면 닫는다.
`PartitionSpec` 은 경로 문자열만 주므로 파티션의 시간 범위를 알 수 없는데, 이 방식은 스킴에 독립적이다.

| 정책 | 슬롯 | **동시 최대** | 파일 수 | 재개봉 | 총 크기 | 건당 | 유실 |
|---|---|---|---|---|---|---|---|
| `lru` | 64 | 64 | 203,449 | 202,999 | 345.6 MiB | 32.90 B | 0 |
| `lru` | 256 | **256** | **450** | 0 | **11.2 MiB** | 1.07 B | 0 |
| `watermark-close` 10일 | 256 | **180** | **450** | 0 | **11.2 MiB** | 1.07 B | 0 |
| `watermark-close` 1일 | 256 | 152 | 108,500 | 108,050 | 193.4 MiB | 18.41 B | 0 |
| `watermark-drop` 1일 | 256 | **45** | **450** | 0 | 17.6 MiB | 1.67 B | **3.462%** |

"동시 최대"는 동시에 열려 있던 파티션의 최대치다. Parquet 라이터마다 row group 버퍼를 들고
있으므로 이 값이 메모리의 대리 지표가 된다.

## 읽어낸 것

### 1. 계획서의 전략 구분이 틀렸다

계획서는 "워터마크 / 유예 시간 / 재개봉 허용" 셋을 나란한 후보로 뒀다.
측정해보니 **그건 같은 축의 다른 이름**이었다.

재개봉을 없애는 조건은 정책 종류가 아니라 **열어두는 창이 지연 상한을 덮는가**다.

- `lru` 슬롯 256 과 `watermark-close` 10일이 **바이트 단위로 동일한 결과**를 낸다
  (11,777,761 bytes / 450 파일). 지연 상한이 10일이므로 10일 창이면 충분하다
- `lru` 슬롯 64(창 ≈ 4.3일)와 `watermark-close` 1일은 **둘 다 터진다**.
  창이 부족하다는 점에서 같은 실패다

처음 측정에서 `watermark-close` 1일이 `lru` 64보다 **더 나빴던 것**(217,227 vs 203,449 파일)도
같은 이야기다. 명시적으로 일찍 닫으니 창이 더 좁아졌을 뿐이다.

### 2. 그렇다면 워터마크의 값어치는 메모리다

같은 결과(450 파일 / 11.2 MiB)를 내면서 동시 최대가 **256 → 180 으로 30% 적다.**

LRU 는 슬롯이 찰 때까지 반납하지 않는다. 워터마크는 이벤트 시각이 지나면 바로 반납한다.
즉 **워터마크는 재개봉을 막는 장치가 아니라, 같은 안전성을 더 적은 메모리로 얻는 장치**다.

180 이라는 값도 의미가 있다 — 지연 상한 10일 × 일당 15 파티션 + 진행 중 분이다.
필요한 슬롯 수를 지연 분포에서 계산할 수 있다는 뜻이고, LRU 로는 그 계산이 불가능하다
(창 크기가 슬롯 수의 함수라 순환 참조가 된다).

### 3. 유실의 대가는 잃은 행만이 아니다

`watermark-drop` 은 메모리를 4배 아끼고(180 → 45) 파일 수도 이상적이다.
대신 3.462% 를 잃는데, **크기는 오히려 1.56배 커진다** (11.2 → 17.6 MiB).

행이 줄었는데 커지는 이유를 열별로 확인했다. `ts` 하나였다.

| | rows | `ts` 압축 전 → 후 | 배율 |
|---|---|---|---|
| 무손실 | 24,480 | 44K → **8K** | 5.4x |
| drop | 23,657 | 43K → **24K** | 1.8x |

`(device_id, ts)` 로 정렬하면 60초 간격이 균일해 `DELTA_BINARY_PACKED` 가 거의 공짜다.
중간중간 행이 빠지면 델타가 60000 / 120000 / 180000 으로 흩어져 그 이점이 무너진다.
다른 열(`device_id`, `value`)은 변화가 없다.

**유실은 데이터만 잃는 게 아니라 남은 데이터의 압축률도 깎는다.** drop 을 택할 때
"3.5% 잃는다"만 계산하면 안 되고 저장 비용이 1.56배가 되는 것까지 봐야 한다.

### 4. 정렬이 지연에 대한 면역을 준다 (ADR-0004 에 없던 근거)

작은 지연(평균 10틱)에서는 재개봉이 0인데도 용량이 **51% 늘었다** (건당 1.02 → 1.55 B).
도착 순서가 흐트러지면서 `ts` 의 인코딩이 깨지는, 위 3번과 같은 메커니즘이다.

**정렬을 켜면 1.07 B 로 돌아온다.** ADR-0004 는 정렬을 행 그룹 프루닝 목적으로 채택했는데,
지연 도착에 대한 방어라는 값어치가 하나 더 있었다. 그때는 알 수 없던 근거다.

## 이 결과의 한계

**지연 분포를 하나만 썼다.** 지수분포 평균 3일 / 상한 10일이다. 실제 지연은 원인마다
다르다 — 네트워크 재시도는 초 단위, 디바이스 시계 오차는 상시, 오프라인 후 일괄 전송은 일 단위.
특히 **상한 없는 지연**(몇 달 뒤 도착)은 어떤 창으로도 못 막고 drop 이나 별도 경로가 필요하다.

**단일 프로세스다.** Kafka 컨슈머 그룹에서 파티션이 리밸런스되면 같은 파티션 경로를
여러 인스턴스가 동시에 열 수 있다. 그건 [PHASE2.md 의 알려진 결함 1번](../PHASE2.md)과 얽힌다.

**메모리를 파티션 수로 대리했다.** 실제 힙 사용량은 재지 않았다.
row group 버퍼가 실제로 얼마나 차 있는지는 파티션당 유입량에 달렸다.

**5% 라는 지연 비율의 근거가 없다.** 실제 값은 운영 데이터를 봐야 안다.
다만 비율보다 **지연의 꼬리 길이**가 결정적이라는 것은 이 측정에서 분명하다 —
창이 상한을 덮으면 비율은 무관하고, 못 덮으면 비율만큼 터진다.
