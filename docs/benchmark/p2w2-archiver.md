## `kill -9` — 미커밋 상한이 중복을 결정한다

실행 12초 시점에 `kill -9` 로 죽이고 재시작했다. 같은 데이터, 같은 설정,
**미커밋 상한(ADR-0006 결정 6)만** 바꿨다.

| | 상한 2,000,000 (발동 안 함) | 상한 50,000 |
|---|---|---|
| 죽은 직후 Kafka 랙 | 367,200 (**커밋 0**) | 65,160 |
| 죽은 직후 로컬 `ready` | 60개 | **0개** |
| 2차 재생 | 367,200 | 65,160 (17.7%) |
| 총 행 수 | 734,400 | **367,200** |
| 고유 행 수 | 367,200 | 367,200 |
| **중복** | **367,200 (100%)** | **0** |
| S3 객체 / 크기 | 120개 / 1.3 MiB | 135개 / 983 KiB |

**유실은 둘 다 0이다.** 고유 행 수가 주입 건수와 정확히 같다 — 커밋 저수위선 규칙이
지켜졌다는 뜻이고, 이게 ADR-0006 결정 1의 검증이다.

**중복은 상한 하나로 100% → 0% 가 된다.** 상한 2,000,000 은 36만 건 데이터에서
한 번도 발동하지 않았고, 닫기 창(1일)도 1일치 데이터에서는 발동하지 않는다.
그래서 **실행 내내 슬롯이 하나도 안 닫혔고 저수위선이 0에서 움직이지 않았다.**
죽는 순간 커밋된 것이 없으니 전부 재생되고, 이미 올라간 것과 겹친다.

대가는 파일 수다. 120개 → 135개(+12.5%). 다만 총 크기는 오히려 작다(1.3 MiB → 983 KiB) —
중복이 사라진 몫이 강제 닫기로 늘어난 파일 오버헤드보다 크기 때문이다.
**이 규모에서는 상한을 낮추는 쪽이 모든 면에서 낫다.**

### `ready` 파일 복구가 중복을 만든다

상한 2,000,000 에서 죽었을 때 로컬 `ready` 에 60개가 남아 있었고, 재시작이 그걸 전부 올렸다.
**그 파일들의 오프셋은 커밋된 적이 없어서 어차피 재생된다** — 같은 데이터가 두 번 올라간다.

지금 코드는 그걸 구분할 수 없다. `ready` 파일이 어느 오프셋 구간을 담는지 모르기 때문에
"올리는 쪽"을 택했고, 그건 유실을 막는 안전한 선택이지만 중복을 보장한다.

[ADR-0006 결정 8](../adr/0006-archiver-durability.md)(푸터 메타데이터에 오프셋 구간)이
여기서 훨씬 강한 근거를 얻는다. 그게 있으면 복구 규칙이 하나로 정해진다.

```
파일의 maxOffset >= 커밋된 오프셋  →  어차피 재생된다. 버린다
파일의 maxOffset <  커밋된 오프셋  →  재생되지 않는다. 반드시 올린다
```

이번 경우 커밋이 0이었으므로 60개 전부 버려도 됐고, 그러면 중복이 0이 됐을 것이다.
**결정 8 은 compaction 을 위한 것이 아니라 복구 정확성에 직접 필요하다.**

단, 상한을 낮춰도 이 창이 완전히 닫히지는 않는다 — `promote` 와 업로드 사이에 죽으면
여전히 `ready` 가 남는다. 상한은 그 창을 좁힐 뿐이다.

## 결정 8 을 구현하고 같은 자리에서 다시 쟀다

푸터에 `(topic, kafka_partition, min_offset, max_offset, writer_id, close_epoch)` 를 넣고,
복구가 그걸 읽어 `maxOffset` 과 커밋 오프셋을 비교하게 했다.
**설정은 그대로 두고**(상한 2,000,000) 같은 지점 — `ready` 에 60개가 쌓인 순간 — 에서 죽였다.

| | 결정 8 전 | 결정 8 후 |
|---|---|---|
| 죽은 직후 `ready` | 60개 | 59개 (1개는 이미 업로드됨) |
| 복구 처리 | 전부 업로드 | **전부 폐기** |
| S3 객체 / 크기 | 120개 / 1.3 MiB | **61개 / 0.7 MiB** |
| 총 행 수 | 734,400 | **374,400** |
| 고유 행 수 | 367,200 | 367,200 |
| **중복** | **367,200 (100%)** | **7,200 (1.96%)** |

**설정을 하나도 안 바꾸고 중복이 100% → 1.96% 가 됐다.** 앞의 표에서 상한을 낮춰 얻은
0% 와 달리 이건 파일을 강제로 닫지 않고 얻은 것이라 파일 수가 늘지 않는다.

`ready` 를 무조건 올리던 것을 푸터로 판단하게 바꾼 것이 전부다.

```
복구: ready 59개 → 올림 0 / 버림 59
```

커밋이 0이었으므로 59개 전부 `maxOffset >= 커밋 오프셋` 에 걸렸다 — 어차피 재생될 구간이다.

### 남은 1.96% 는 다른 창이다

정확히 파일 하나(7,200행 = 디바이스 5 × 1,440점)다. **죽기 직전에 S3 로 이미 올라간 파일**이다.

업로드는 성공했는데 그 오프셋의 커밋은 아직이었다. 재생이 같은 행을 다시 써서 새 파일로 올린다.
**결정 8 로는 못 막는다** — 데이터가 `ready/` 가 아니라 이미 S3 에 있기 때문이다.

이 창의 크기는 **"마지막 커밋 이후 올린 파일 수"** 로 정해진다. 상한을 낮춰 커밋을 자주 하면
같이 줄어든다. 완전히 없애려면 업로드와 커밋이 한 트랜잭션이어야 하는데 S3 와 Kafka 사이에는
그런 것이 없다.

### `ready` 가 쌓이기 전에 죽으면 중복이 0이다

같은 조건에서 `ready` 14개 / `inflight` 46개 시점에 죽인 경우:

| | 값 |
|---|---|
| 복구 | ready 14개 → 올림 0 / 버림 14 |
| S3 객체 | 60개 / 0.7 MiB |
| 총 행 수 | 367,200 |
| **중복** | **0** |

아직 아무것도 업로드되지 않았으므로 위의 창 자체가 열리지 않았다.
`inflight` 46개는 불변식 2대로 그냥 버려지고 재생으로 복구된다.

### 조회 쪽 dedup 이 실제로 해소한다

파일명 앞의 닫힌 시각으로 순서를 정하는 것까지 확인했다.

```sql
SELECT * FROM read_parquet('s3://.../k9e/**/*.parquet', hive_partitioning = 1, filename = 1)
QUALIFY row_number() OVER (PARTITION BY tenant_id, device_id, key, ts ORDER BY filename DESC) = 1
```

```
총 행 수      : 374,400
dedup 후 행 수: 367,200   ← 파일명 순서로 해소
```

`DISTINCT` 와 값이 같지만 성질이 다르다 — `DISTINCT` 는 완전히 같은 행만 합치고,
이쪽은 **같은 `(tenant, device, key, ts)` 에 값이 다를 때도 어느 쪽이 이길지가 정해진다.**
다만 이번 데이터에서는 두 복사본의 값이 같아서 그 성질 자체를 가른 것은 아니다.

### 복구가 "올린다"를 고르는 경우는 지금 코드에서 안 나온다

세 번 재는 동안 `올림` 은 한 번도 0이 아닌 적이 없었다. 우연이 아니다 —
`drainUploads` 가 파일마다 `업로드 → complete → 삭제` 를 끝내고 나서야 커밋하므로,
**`ready` 에 남은 파일의 오프셋은 항상 커밋 저수위선 뒤에 있다.**

그렇다고 "복구는 무조건 버린다"로 짜면 안 된다. 그 결론은 `drainUploads` 의 순서에 의존하고,
업로드를 병렬화하거나 커밋 지점을 옮기는 순간 조용히 깨진다. 그때 깨지는 방식이 **유실**이다.
푸터에 좌표가 있으면 순서 논증에 기대지 않고 파일이 스스로 증명한다.

## 리밸런스 — 두 인스턴스로 재봤다

3,672,000건(10일치)을 A 가 읽는 도중에 B 를 같은 그룹에 넣었다.
`partition.assignment.strategy` 가 `RangeAssignor` 우선이라 **EAGER** 프로토콜이다 —
A 는 4개를 전부 회수당하고 2개만 돌려받는다. 최악의 경우를 그대로 재는 셈이다.

| | A | B |
|---|---|---|
| 소비 = 기록 | 2,143,923 | 1,528,077 |
| 업로드 파일 | 405 | 255 |
| 최대 미커밋 | 210,278 | 223,155 |
| **최대 회수 시간** | **937 ms** (4개 / 파일 120개) | 947 ms |
| 소요 | 18.8s | 16.5s |

| 대조 | 값 |
|---|---|
| A + B 기록 | 2,143,923 + 1,528,077 = **3,672,000** |
| **S3 총 행 수** | **3,672,000** |
| **고유 행 수** | **3,672,000** (중복 0) |
| Kafka 랙 | 0 |
| S3 객체 | 660개 / 6.9 MiB |

**인계 지점에서 유실도 중복도 없다.** 두 인스턴스의 기록 수 합이 주입 건수와 정확히 같고,
S3 총 행 수도 같다 — 회수 시점에 A 가 flush → 업로드 → commitSync 를 동기로 끝내고
B 가 그 커밋 지점부터 이어받았다는 뜻이다.

### 대가는 파일 10% 다

이상적인 파일 수는 3 테넌트 × 5 키 × 10 날짜 × 4 Kafka 파티션 = **600개**인데 660개가 나왔다.
회수 순간 열려 있던 슬롯 60개가 각각 A 의 파일과 B 의 파일로 갈렸다.
**리밸런스 한 번이 그때 열린 슬롯 수만큼 파일을 쪼갠다.**

### 임계는 멀지만, 여기서 멀 뿐이다

ADR-0006 이 남긴 질문은 "회수 안의 flush → upload → commitSync 가
`max.poll.interval.ms` 를 넘길 수 있는가"였다. 재보니 **937 ms 대 300,000 ms — 320배 여유**다.

다만 이 숫자를 그대로 믿으면 안 된다. 회수 시간은 **그때 열린 슬롯 수 × 업로드 왕복**인데,
여기서는 파일당 7.8 ms 였고 그건 같은 머신의 MinIO 라서다. 실제 S3 왕복이 50 ms 라면
같은 120개가 6초, 임계는 파일 6,000개 근처로 내려온다.
[W1](p2w1-partition-closing.md) 이 잰 워터마크 7일 창의 동시 파티션 180개 규모에서는
아직 여유가 있지만, **창을 늘리거나 업로드가 느려지면 좁혀지는 축**이다.

## 거부된 키가 파티션을 막지 않는다

깨진 메시지와 **다른 경로**로 갈려야 한다 — 그쪽은 디코딩에서 죽고 이쪽은
`PartitionValues` 검증에서 죽는다. 같은 카운터로 세면 디바이스가 보낸 키 하나가
경로 탈출(`../../etc/passwd`)을 시도한 것을 못 본다.

정상 5,000 + 깨진 200 + 못 쓰는 키 300(`../../etc/passwd`, `temp/erature`, `..`, 공백 포함)을 섞었다.

| | 값 |
|---|---|
| 소비 | 5,500 |
| **기록** | **5,000** |
| **파싱 실패** | **200** |
| **거부** | **300** |
| S3 총 행 수 | 5,000 |
| Kafka 랙 | 0 |

정확히 셋으로 갈린다. 랙이 0이라는 것이 요점이다 — 어느 쪽도 파티션을 막지 않았다.

## 재생 구간의 크기가 숫자로 나왔다

**최대 미커밋 100,800 오프셋.** 20만 건을 처리하는 동안 절반이 미커밋 상태였다는 뜻이다.

ADR-0006 이 지적한 구조가 그대로 보인다 — 정렬 모드에서 행은 슬롯이 닫힐 때까지 힙에 있고,
슬롯은 이벤트 시각으로 닫힌다. 닫기 창이 1일이고 데이터도 1일치라 **실행이 끝날 때까지
아무 슬롯도 닫히지 않았다.** 그래서 커밋 저수위선이 거의 움직이지 않았다.

이게 곧 크래시 시 재생해야 할 양이다. 창을 7일(기본값)로 두면 이 값이 훨씬 커진다.
**닫기 창은 파일 품질만이 아니라 복구 비용을 정한다.**

## 1천만 건 규모

28일치 10,281,600건을 단일 인스턴스로 통과시켰다.

| | 값 |
|---|---|
| 소비 = 기록 | **10,281,600** |
| 파싱 실패 / 거부 | 0 / 0 |
| 업로드 파일 | **1,680** |
| 최대 미커밋 | 223,838 오프셋 |
| 소요 | 55.2s (**186,261 행/s**) |
| **S3 총 행 수** | **10,281,600** |
| **고유 행 수** | **10,281,600** (중복 0) |
| Kafka 랙 | 0 |
| S3 객체 | 1,680개 / 19,325,847 bytes (18.4 MiB) |

**파일 수가 이상값과 정확히 같다.** 3 테넌트 × 5 키 × 28 날짜 × 4 Kafka 파티션 = 1,680 —
재개봉이 한 번도 없었다. 워터마크 닫기(창 1일)가 27번 발동하는 동안 닫힌 파티션에
데이터가 다시 온 적이 없다는 뜻이다. ADR-0005 가 라이터 단위로 확인한 성질이
Kafka 를 거쳐도 유지된다.

처리량은 186,261 행/s 로, 36만 건 실행의 64,500 행/s 보다 2.9배 빠르다 — JIT 예열이
분모에 덜 섞였기 때문이다. Phase 1 의 직접 적재 1,337,299 pt/s 보다는 여전히 7.2배 느리다.

### Kafka 파티션 수가 저장 비용을 곱한다

같은 데이터 형태인데 Phase 1 보다 행당 바이트가 나쁘다.

| | 행/파일 | bytes/파일 | **bytes/행** |
|---|---|---|---|
| [Phase 1 W3](w3-s3-ingest.md) (Kafka 없음) | 24,480 | 25,281 | **1.033** |
| **W2 (Kafka 파티션 4)** | **6,120** | **11,504** | **1.879** |

**같은 행이 82% 더 큰 자리를 차지한다.** 파티션 스킴도, 코덱도, 정렬도, 라이터 버전도 같다.
다른 것은 하나뿐이다 — **Kafka 파티션마다 라이터를 따로 두므로**(ADR-0006 결정 5)
`(tenant, date, key)` 하나가 4개 파일로 쪼개진다.

두 점으로 파일당 고정 비용과 행당 실비를 가를 수 있다.

```
24,480p + F = 25,281        p ≈ 0.750 bytes/행   (실제 데이터)
 6,120p + F = 11,504        F ≈ 6,911 bytes/파일 (푸터·스키마·딕셔너리·행그룹 메타)
```

두 식이 맞아떨어진다(예측 11,503 / 실측 11,504). 그러면 **파일당 6.9 KiB 는 행 수와 무관한
고정비**이고, 저장 바이트에서 차지하는 비중은 파일이 작을수록 커진다.

| | 고정비 비중 |
|---|---|
| Phase 1 (24,480 행/파일) | 27% |
| W2 (6,120 행/파일) | **60%** |

[W3 에서 `date/hour` 를 기각한 것](w3-partition-granularity.md)과 **같은 메커니즘**이다.
그때는 시간 축을 쪼개서 67.5%가 오버헤드가 됐고, 지금은 Kafka 파티션 축이 쪼갠다.
차이는 이번엔 **피할 수 없다**는 것이다 — 파티션별 라이터는 워터마크 오염을 막는 유일한
방법이고(결정 5), 그걸 포기하면 재개봉이 터진다.

1년치로 늘리면 21,900 파일 / 약 240 MiB 로, Phase 1 의 132.0 MiB 대비 1.82배다.
**이 손해는 Kafka 파티션 수에 비례해 커진다** — 12개면 3배다.
그래서 Phase 3 의 compaction 은 "있으면 좋은 것"이 아니라 **결정 5의 대가를 되돌리는 일**이다.

## 구현하며 드러난 것

### 1. `auto.offset.reset=none` 은 첫 실행도 막는다

ADR-0006 은 이 값을 "트렁케이션을 조용히 건너뛰지 않게" 하려고 정했다.
그런데 그대로 두면 **커밋 이력이 없는 첫 기동도 `NoOffsetForPartitionException` 으로 죽는다.**

ADR 에 "기동 시 `committed < beginning` 이면 거부"라고 써놓고 그 처리를 구현하지 않아
예외가 먼저 터졌다. 두 경우를 손으로 갈랐다.

- 커밋 없음 → 첫 기동. 처음부터 읽되 **로그로 남긴다**
- `committed < beginning` → 잘려나갔다. **거부한다.** 처음부터 읽으면 전부 재처리하고
  끝에서 읽으면 그 구간이 사라진다 — 어느 쪽도 자동으로 고를 수 없다

### 2. 끝을 판단하는 방법을 두 번 틀렸다

상시 실행이 아닌 **끝이 있는 실행**에서 언제 마무리할지가 생각보다 까다로웠다.

| 시도 | 결과 |
|---|---|
| "진행 중인 단위가 없으면 끝" | **영원히 폴링.** 슬롯은 닫기 창이 지나야 닫히므로 0이 되지 않는다 |
| "빈 poll 이 5번 연속이면 끝" | **한 건도 안 읽고 끝남.** 그룹 조인 중에도 poll 은 비어 있다 |
| `position >= endOffset` 으로 따라잡음 판정 | 동작. 타이밍에 의존하지 않는다 |

두 번째 실패가 특히 조용했다 — 1차 실행이 "소비 0 / 기록 0 / 5.6초"로 **성공한 것처럼**
끝났다. 건수 대조를 하지 않았으면 넘어갔을 것이다.

### 3. 깨진 메시지가 파티션을 막지 않는다

`{"broken":N}` 500건을 정상 5,000건과 섞어 흘렸다.

| | 값 |
|---|---|
| 소비 | 5,500 |
| **기록** | **5,000** |
| **파싱 실패** | **500** |
| 거부 | 0 |
| 업로드 파일 | 10 |

정확히 갈린다. archiver 에서 한 건이 예외를 던지면 그 메시지가 파티션을 영구히 막으므로
`TelemetryCodec.decode` 는 던지지 않고 `null` 을 돌려주고, 호출자가 세고 넘어간다.
코드 주석의 주장이 아니라 실측이다.

### 4. 처리량

주입 286,740 msg/s, 적재 200,000건 3.1초(약 64,500건/s). Phase 1 의 직접 적재
1,337,299 pt/s 보다 20배 느린데, Kafka 왕복과 역직렬화가 붙었기 때문이다.
다만 이 숫자는 최적화를 하나도 하지 않은 상태다.

## 이 결과의 한계

**값이 다른 중복을 만들어보지 않았다.** dedup 질의가 파일명 순서로 해소하는 것은 확인했지만,
두 복사본의 값이 같은 데이터였다. 재생본과 원본의 값이 갈리는 상황(생성기가 결정론적이라
이 하네스에서는 안 생긴다)에서 "나중 파일이 이긴다"가 의도한 결과인지는 아직 판단하지 않았다.

**dedup 의 질의 비용을 재지 않았다.** ADR-0006 이 "조회 쪽에 dedup 이 상시 걸린다"를
대가로 적었는데, 그 비용이 ADR-0004 가 정렬로 얻은 전송 −52% 위에 얼마나 얹히는지는
[W4 벤치](w4-duckdb-baseline.md)를 dedup 을 켠 채로 다시 돌려야 나온다.

**미커밋 상한 강제 닫기가 실제로 발동한 실행은 상한 50,000 하나뿐이다.**
워터마크 닫기는 10일치 리밸런스 실행에서 발동했지만, 두 축이 동시에 걸리는 경우는 안 봤다.

**S3 가 아니라 같은 머신의 MinIO 다.** 업로드 왕복이 실제 S3 보다 훨씬 짧고,
그 값이 회수 시간과 커밋 지연에 직접 들어간다. 위의 회수 320배 여유는 이 조건의 숫자다.

**측정 사이에 S3 프리픽스를 비워야 한다.** 리밸런스 측정에서 직전 3일치 잔여분이
10일치 결과에 30% 중복으로 보였다 — 코드가 아니라 하네스 문제였다.
그래서 `--mode=clear` 를 붙였다.
