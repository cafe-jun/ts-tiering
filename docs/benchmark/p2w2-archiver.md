# Phase 2 W2 — archiver 종단 검증

측정일: 2026-08-16
환경: macOS (darwin 23.4.0, Apple Silicon), Java 17,
Redpanda `v26.1.16`, MinIO `RELEASE.2025-09-07T16-13-09Z`, kafka-clients 4.3.0
데이터: 1일치 367,200건 (테넌트 3 × 디바이스 17 × 키 5, 60초 주기)
설정: Kafka 파티션 4, 닫기 창 1일, 미커밋 상한 2,000,000

```
docker compose -f deploy/docker-compose.dev.yml up -d
./gradlew :bench:archive --args="--mode=produce --days=1 --devices-per-tenant=17 --interval-seconds=60"
./gradlew :bench:archive --args="--mode=archive --max-records=200000"   # 중단
./gradlew :bench:archive --args="--mode=archive"                        # 재시작

```

**충족.** 유실도 중복도 없다.

> 중복이 0인 것은 1차가 **정상 종료**했기 때문이다 — 루프를 빠져나와
> `closeAllWriters` → 업로드 → 커밋을 마쳤다. `kill -9` 면 마지막 배치가 재생되어
> 중복이 생기고, 그건 [ADR-0006](../adr/0006-archiver-durability.md) 이
> "허용하되 결정론적으로 해소"로 정한 부분이다. 그 경로는 아직 재지 않았다.

## 재생 구간의 크기가 숫자로 나왔다

**최대 미커밋 100,800 오프셋.** 20만 건을 처리하는 동안 절반이 미커밋 상태였다는 뜻이다.

ADR-0006 이 지적한 구조가 그대로 보인다 — 정렬 모드에서 행은 슬롯이 닫힐 때까지 힙에 있고,
슬롯은 이벤트 시각으로 닫힌다. 닫기 창이 1일이고 데이터도 1일치라 **실행이 끝날 때까지
아무 슬롯도 닫히지 않았다.** 그래서 커밋 저수위선이 거의 움직이지 않았다.

이게 곧 크래시 시 재생해야 할 양이다. 창을 7일(기본값)로 두면 이 값이 훨씬 커진다.
**닫기 창은 파일 품질만이 아니라 복구 비용을 정한다.**

## 구현하며 드러난 것

### 1. `auto.offset.reset=none` 은 첫 실행도 막는다

ADR-0006 은 이 값을 "트렁케이션을 조용히 건너뛰지 않게" 하려고 정했다.
그런데 그대로 두면 **커밋 이력이 없는 첫 기동도 `NoOffsetForPartitionException` 으로 죽는다.**

ADR 에 "기동 시 `committed < beginning` 이면 거부"라고 써놓고 그 처리를 구현하지 않아
예외가 먼저 터졌다. 두 경우를 손으로 갈랐다.

- 커밋 없음 → 첫 기동. 처음부터 읽되 **로그로 남긴다**
- `committed < beginning` → 잘려나갔다. **거부한다.** 처음부터 읽으면 전부 재처리하고
  끝에서 읽으면 그 구간이 사라진다 — 어느 쪽도 자동으로 고를 수 없다

### 2. 끝을 판단하는 방법을 두 번 틀렸다

상시 실행이 아닌 **끝이 있는 실행**에서 언제 마무리할지가 생각보다 까다로웠다.

| 시도 | 결과 |
|---|---|
| "진행 중인 단위가 없으면 끝" | **영원히 폴링.** 슬롯은 닫기 창이 지나야 닫히므로 0이 되지 않는다 |
| "빈 poll 이 5번 연속이면 끝" | **한 건도 안 읽고 끝남.** 그룹 조인 중에도 poll 은 비어 있다 |
| `position >= endOffset` 으로 따라잡음 판정 | 동작. 타이밍에 의존하지 않는다 |

두 번째 실패가 특히 조용했다 — 1차 실행이 "소비 0 / 기록 0 / 5.6초"로 **성공한 것처럼**
끝났다. 건수 대조를 하지 않았으면 넘어갔을 것이다.

### 3. 깨진 메시지가 파티션을 막지 않는다

`{"broken":N}` 500건을 정상 5,000건과 섞어 흘렸다.

| | 값 |
|---|---|
| 소비 | 5,500 |
| **기록** | **5,000** |
| **파싱 실패** | **500** |
| 거부 | 0 |
| 업로드 파일 | 10 |

정확히 갈린다. archiver 에서 한 건이 예외를 던지면 그 메시지가 파티션을 영구히 막으므로
`TelemetryCodec.decode` 는 던지지 않고 `null` 을 돌려주고, 호출자가 세고 넘어간다.
코드 주석의 주장이 아니라 실측이다.

### 4. 처리량

주입 286,740 msg/s, 적재 200,000건 3.1초(약 64,500건/s). Phase 1 의 직접 적재
1,337,299 pt/s 보다 20배 느린데, Kafka 왕복과 역직렬화가 붙었기 때문이다.
다만 이 숫자는 최적화를 하나도 하지 않은 상태다.

## 이 결과의 한계

**`kill -9` 를 재지 않았다.** 정상 종료만 검증했다. 중복이 실제로 어느 규모로 생기는지,
그리고 조회 쪽 dedup 이 그걸 결정론적으로 해소하는지는 미검증이다 —
ADR-0006 결정 8(파일명에 닫힌 시각, 푸터 메타데이터에 오프셋 구간)도 아직 구현 전이다.

**단일 인스턴스다.** 리밸런스 경로(`onPartitionsRevoked` 에서 flush → upload → commit)는
코드에 있지만 실제로 두 인스턴스를 띄워 재지 않았다.

**데이터가 1일치뿐이라 닫기 창이 한 번도 발동하지 않았다.** 워터마크 닫기와
미커밋 상한 강제 닫기 둘 다 이 실행에서는 트리거되지 않았다.
그 경로들은 [W1 측정](p2w1-partition-closing.md)에서 라이터 단위로만 검증됐다.

**거부된 키(`rejected`)는 흘려보지 않았다.** 깨진 메시지는 아래에서 확인했지만,
`PartitionValues` 검증에 걸리는 키(`../x` 같은)를 실제로 Kafka 로 보낸 적은 없다.
