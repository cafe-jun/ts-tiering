# ADR-0003 — 쿼리 엔진

- 상태: 채택 (**2026-08-11 개정** — 아래 '개정' 절)
- 일자: 2026-08-09
- 관련: W4, [벤치마크](../benchmark/w4-duckdb-baseline.md), [ADR-0001](0001-parquet-library.md)

## 맥락

이 ADR 은 **뒤늦게 쓴다.** DuckDB 는 W1 시점의 계획서에 이미 들어 있었고 근거는 어디에도 없었다.
그런데 [ADR-0001](0001-parquet-library.md)이 "쿼리는 DuckDB/Athena 가 맡는다"를 전제로
Hadoop 제거를 정당화하고 있다. 전제가 결론을 떠받치고 있는데 전제 쪽에 문서가 없는 상태였다.

W4 실측이 나온 김에 근거를 세운다.

### 왜 Java 로는 안 되는가

선택의 여지가 없는 부분이 먼저다. ADR-0001 에서 Hadoop 을 걷어내면서
`ParquetReadOptions.Builder` 생성자가 Hadoop MapReduce 클래스를 로드하는 문제에 막혀
**Java 쪽 Parquet 레코드 읽기를 포기했다.** 우회 지점이 없었다.

즉 쿼리는 반드시 외부 엔진이 맡아야 한다. 질문은 "어떤 엔진인가"뿐이다.

## 후보

| 후보 | 성격 |
|---|---|
| **DuckDB** | 단일 바이너리 임베디드. `httpfs` 로 S3 Parquet 직접 조회 |
| Trino / Presto | 분산 쿼리 엔진. 코디네이터 + 워커 |
| ClickHouse (local) | 컬럼 지향 DB. `clickhouse-local` 로 Parquet 조회 가능 |
| Polars / pyarrow | 파이썬 데이터프레임. Parquet 읽기는 되지만 SQL 계층이 얇다 |
| Athena | 관리형. Glue 카탈로그 필요, 실 AWS 필요 |

## 개정 (2026-08-11) — Athena 는 범위 밖이다

이 ADR 은 원래 "로컬은 DuckDB, 클라우드 비교군은 Athena" 로 결정했고, 그 첫 번째 근거가
Phase 1 종료 조건 3번("DuckDB와 Athena 비교")이었다. **그 종료 조건은 폐기됐다** —
AWS 를 쓰지 않기로 확정했다 ([PHASE1.md](../PHASE1.md) 참고).

**개정된 결정: 쿼리 엔진은 DuckDB. 관리형 엔진과의 비교는 수행하지 않으며 미검증으로 남는다.**

아래 근거 1(Athena 동형성)은 **기각된 전제**다. 다만 완전히 무의미하지는 않다 —
Hive 파티셔닝 규약을 지킨 덕분에 나중에 Athena/Glue 로 옮길 여지는 남아 있고,
그건 이식 가능성이지 비교 근거가 아니다.

근거 2~4(인프라 0 / `EXPLAIN` 가시성 / Hive 네이티브 지원)는 그대로 유효하고,
그 셋만으로도 선택은 바뀌지 않는다.

## 결정 (원문)

**로컬 측정은 DuckDB, 클라우드 비교군은 Athena 로 간다.**

### 1. Athena 와 같은 모델이라 비교가 성립한다

Phase 1 의 종료 조건 3번이 "DuckDB와 Athena 양쪽에서 같은 쿼리를 돌린 비교 결과"다.
즉 DuckDB 는 도구이기 전에 **측정 대상의 한 축**이다.

둘은 "S3 의 Parquet 을 가리키고 SQL 을 던진다"는 동일한 모델이라 같은 쿼리가 그대로 돈다.
Trino 도 같은 모델이지만 클러스터를 세워야 해서, "단일 노드 vs 관리형"이라는
비교 축이 "클러스터 vs 관리형"으로 흐려진다.

### 2. 인프라가 0이다

Phase 1 은 "코드를 많이 만드는 게 목표가 아니다. 산출물은 측정 결과표다"로 시작한다.
DuckDB 는 JDBC 의존성 하나에 `INSTALL httpfs` 한 줄이면 끝난다.
Trino 는 코디네이터·워커·카탈로그 설정이 붙는데, 그 시간은 측정에 기여하지 않는다.

### 3. `EXPLAIN ANALYZE` 가 필요한 지표를 정확히 준다

이게 결정적이었다. 측정 지표표의 "쿼리당 스캔 바이트"는 파티셔닝 효과의 **유일한 직접 증거**인데,
DuckDB 는 그걸 그대로 찍어준다.

```
File Filters: (date BETWEEN '2026-03-01'::DATE AND '2026-03-08'::DATE)
              (tenant = '00000000-007e-4a47-0000-000000000000')
Scanning Files: 7/1095
```

파티션 열이 파일 필터로 밀려 내려갔는지, 몇 개 중 몇 개를 열었는지가 한눈에 나온다.
벤치 하네스가 이 줄을 파싱해 결과표의 "프루닝" 열을 만든다.
Polars 나 pyarrow 로는 이만큼의 계획 가시성을 얻기 어렵다.

### 4. Hive 파티셔닝을 네이티브로 이해한다

`hive_partitioning = 1` 하나로 경로의 `key=value` 를 컬럼으로 복원한다.
W3 에서 파티션 경로를 Hive 스타일로 쓴 이유가 이것이고, Athena/Glue 도 같은 규약을 쓴다.
포맷을 한 번 정하면 양쪽에서 통한다.

## W4 실측 (근거)

134,028,000 행 / 5,475 객체 / 132.0 MiB 를 MinIO 에 두고 조회했다.
상세는 [벤치마크 문서](../benchmark/w4-duckdb-baseline.md).

| | 스캔 파일 | 프루닝 | 스캔량 | p50 |
|---|---|---|---|---|
| Q1 (7일) | 7 / 1,095 | 99.4% | 0.22 MiB | 1,084.9ms |
| Q2 (1년 집계) | 365 / 1,095 | 66.7% | 11.50 MiB | 1,136.2ms |
| Q3 (1개월 전체) | 93 / 1,095 | 91.5% | 2.93 MiB | 1,071.8ms |
| glob 나열만 | — | — | 0 | 531ms |

**되는 것**: 프루닝이 확실히 걸린다. Q1 은 1,095개 중 7개만 연다.
Java 로 못 하게 된 일을 DuckDB 가 대신할 뿐 아니라, 계획 가시성까지 준다.

**드러난 것**: 스캔량이 52배 차이인데 지연은 5% 차이다.
531ms — 지연의 절반이 객체 나열에 든다. 이건 DuckDB 의 결함이 아니라
**32.3 KiB 짜리 파일 1,095개**라는 데이터 형상의 문제다. Athena 도 같은 LIST 를 해야 한다.

## 대가

- **네이티브 라이브러리가 딸려온다.** `duckdb_jdbc` 는 플랫폼별 바이너리를 품는다.
  ADR-0001 이 Arrow 를 기각한 이유와 같은 성질인데, 여기서는 받아들인다 —
  **벤치 모듈에만 있고 배포 아티팩트에는 들어가지 않기 때문**이다.
  Phase 2 의 `query` 모듈이 DuckDB 를 쓰게 되면 그때 다시 판단해야 한다
- **단일 노드다.** 데이터가 한 대의 메모리·디스크를 넘어가는 순간 선택지가 아니다.
  그 분기점은 **재지 않았다** — W8 이 취소되면서 미검증으로 남는다
- **동시성을 재지 않았다.** 대시보드가 초당 수백 번 읽는 상황은 이 결정의 근거에 없다.
  Phase 2 의 쿼리 라우터를 설계할 때 다시 확인할 것

## 이 결정이 바꾼 것

W4 측정 결과가 **W5~W6 의 지표를 바꿨다.**

계획서는 스킴 비교 지표로 "p50/p95"와 "스캔 바이트"를 나란히 뒀는데,
531ms 의 나열 비용이 스킴 간 차이를 전부 덮어버린다.
따라서 W5~W6 은 **스캔 파일 수 / 프루닝 비율**을 중심 지표로 삼는다.
그 값은 `EXPLAIN ANALYZE` 에서 정확히 나오고 스킴에 따라 확실히 달라진다.
