# ADR-0005 — 파티션 닫기 전략

- 상태: 채택
- 일자: 2026-08-15
- 관련: Phase 2 W1, [벤치마크](../benchmark/p2w1-partition-closing.md), [ADR-0004](0004-partition-scheme.md)

## 맥락

Parquet 은 append 를 지원하지 않는다. 파티션 파일을 닫고 나서 그 파티션에 데이터가 더 오면
새 파일을 열 수밖에 없고, 그게 곧 small file 이다.

Phase 1 에서는 이 문제가 보이지 않았다. 합성 생성기가 ts 오름차순으로 방출해서
닫힌 파티션에 데이터가 다시 올 일이 없었다. 축출이 5,411회 일어나도 재개봉은 0이었다.

**Kafka 는 시간순으로 오지 않는다.** 네트워크 재시도, 파티션 리밸런스, 디바이스 시계 오차,
오프라인 후 일괄 전송이 모두 지연 도착을 만든다.

## 문제의 크기

지연 5%(지수분포 평균 3일 / 상한 10일)를 30일치에 주입했다.

| 라이터 슬롯 | 파일 수 | 총 크기 | NDJSON 대비 |
|---|---|---|---|
| (지연 없음) | 450 | 11.2 MiB | 184x |
| 64 | 203,449 | 345.6 MiB | 6.0x |
| 16 | 1,019,755 | 1,708 MiB | **1.2x** |

Parquet 을 쓸 이유가 사라진다. Phase 1 의 모든 결론이 무효가 되는 규모다.

## 측정이 바꾼 프레이밍

[PHASE2.md](../PHASE2.md) 는 후보를 "워터마크 / 유예 시간 / 재개봉 허용" 셋으로 적었다.
**측정해보니 그건 같은 축의 다른 이름이었다.**

재개봉 여부를 가르는 것은 정책 종류가 아니라 **열어두는 창이 지연 상한을 덮는가**다.

- `lru` 슬롯 256 과 `watermark-close` 10일이 **바이트 단위로 동일한 결과**를 낸다
  (11,777,761 bytes / 450 파일)
- `lru` 슬롯 64(창 ≈ 4.3일)와 `watermark-close` 1일은 둘 다 터진다. 같은 실패다

따라서 실제 결정 축은 둘이다. **(1) 창을 얼마나 열어둘 것인가**, **(2) 창을 벗어난 것을
버릴 것인가**.

## 결정

### 1. 이벤트 시각 워터마크로 닫는다. LRU 축출에 맡기지 않는다

```java
ClosePolicy.watermarkClose(Duration.ofDays(N))
```

같은 결과를 내면서 **동시에 열린 파티션이 30% 적다** (256 → 180).
LRU 는 슬롯이 찰 때까지 반납하지 않고, 워터마크는 이벤트 시각이 지나면 바로 반납한다.

더 중요한 건 **계산 가능해진다**는 점이다. 필요한 슬롯 수 = 지연 상한 × 일당 파티션 수 + 진행분.
LRU 로는 이 계산이 안 된다 — 창 크기가 슬롯 수의 함수라 순환 참조가 된다.
"슬롯을 몇 개 줘야 하나"에 답할 수 없는 설계는 운영에 올릴 수 없다.

워터마크는 **이벤트 시각 기준**이고 슬롯별 마지막 ts 만 본다.
`PartitionSpec` 이 경로 문자열만 주므로 파티션의 시간 범위를 파싱하면 스킴에 묶이는데,
이 방식은 스킴에 독립적이다.

### 2. 기본은 무손실(`watermark-close`)로 간다

`watermark-drop` 은 메모리를 4배 아끼지만(180 → 45 파티션) 3.462% 를 잃는다.
cold 계층은 "원본이 여기 다 있다"가 존재 이유이므로 기본값이 될 수 없다.

**유실의 대가가 잃은 행만이 아니라는 것도 근거다.** drop 은 행이 3.46% 적은데
크기가 **1.56배 커진다** (11.2 → 17.6 MiB). 원인은 `ts` 열 하나다.

| | `ts` 압축 전 → 후 | 배율 |
|---|---|---|
| 무손실 | 44K → **8K** | 5.4x |
| drop | 43K → **24K** | 1.8x |

`(device_id, ts)` 정렬에서 60초 간격이 균일해야 `DELTA_BINARY_PACKED` 가 값어치를 하는데,
중간이 빠지면 델타가 흩어져 무너진다. **"3.5% 잃고 메모리를 아낀다"가 아니라
"3.5% 잃고 저장 비용이 1.56배가 되면서 메모리를 아낀다"** 가 정확한 교환이다.

### 3. 창 크기는 지연 분포에서 정한다. 기본 7일

지연 상한을 덮으면 비율은 무관하고, 못 덮으면 비율만큼 터진다.
따라서 튜닝해야 할 값은 **꼬리 길이**다.

운영 데이터가 없으므로 7일을 기본으로 둔다 — 디바이스가 일주일 오프라인이었다가
일괄 전송하는 경우까지 덮는 값이다. Phase 2 에서 실제 지연 분포를 관측하면 다시 정한다.

슬롯 수는 그에 맞춰 `창(일) × 일당 파티션 수 × 1.2` 로 잡는다.

## 대가

- **메모리가 창에 비례한다.** 7일 창 × 일당 15 파티션 = 126 슬롯.
  파티션 스킴이 잘게 쪼개질수록(스킴 C 는 일당 255) 이 값이 커진다 —
  ADR-0004 가 스킴 C 를 기각한 이유가 여기서 한 겹 더 붙는다
- **창을 벗어난 데이터는 여전히 재개봉을 만든다.** 무손실을 택했으므로 파일이 쪼개진다.
  상한 없는 지연(몇 달 뒤 도착)은 어떤 창으로도 못 막는다 — 별도 경로가 필요하고,
  그건 Phase 3 의 `compactor` 와 얽힌다
- **워터마크 스윕이 8,192행마다 돈다.** 행마다 하면 O(열린 슬롯)이 곱해진다.
  그만큼 닫기가 늦어지지만 이 규모에서는 무시할 수준이다

## 부수 효과: ADR-0004 의 정렬 결정이 지연에도 방어가 된다

작은 지연(평균 10틱)에서는 재개봉이 0인데도 용량이 51% 늘었다 (건당 1.02 → 1.55 B).
도착 순서가 흐트러지면 `ts` 인코딩이 깨지기 때문이고, 위 2번과 같은 메커니즘이다.

**정렬을 켜면 1.07 B 로 돌아온다.** ADR-0004 는 정렬을 행 그룹 프루닝 목적으로 채택했는데,
지연 도착 방어라는 값어치가 하나 더 있었다. 그때는 알 수 없던 근거이므로 여기 적어둔다.

## 남은 질문

- **컨슈머 그룹 리밸런스.** 같은 파티션 경로를 여러 인스턴스가 동시에 열면 워터마크가
  인스턴스마다 달라진다. [PHASE2.md 의 알려진 결함 1번](../PHASE2.md)(파일명 충돌)과 얽힌다
- **실제 힙 사용량.** 파티션 수로 대리했을 뿐 재지 않았다.
  row group 버퍼가 실제로 얼마나 차는지는 파티션당 유입량에 달렸다
- **상한 없는 지연의 처리.** 버릴지, 격리 파티션으로 보낼지, compactor 에 맡길지
