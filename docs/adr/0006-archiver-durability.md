# ADR-0006 — archiver 의 내구성 계약

- 상태: 채택 · 구현 완료 (결정 1~8 전부)
- 일자: 2026-08-15 (구현·검증 2026-08-16)
- 관련: Phase 2 W2, [ADR-0005](0005-partition-closing.md), [ADR-0004](0004-partition-scheme.md), [ADR-0001](0001-parquet-library.md)

## 맥락

`PHASE2.md` 의 W2 는 "Kafka 컨슈머 → PartitionedParquetWriter → S3ObjectStore" 를 잇는
배선 작업으로 적혀 있었다. 리스크표도 "중복 허용 + 조회 시 중복 제거로 간다"는 한 줄이었다.

구현 전에 정확성 설계를 여러 관점에서 분석한 결과, **배선 문제가 아니었다.**
Phase 1 이 만든 라이터의 성질과 Kafka 의 오프셋 모델이 근본적으로 어긋난다.

## 문제: 커밋은 프리픽스인데 내구성 경계는 희소하다

Kafka 는 파티션당 오프셋 스칼라 하나만 커밋한다. 표현할 수 있는 것은
**"이 오프셋 앞은 전부 끝났다"** 는 프리픽스뿐이다.

그런데 이 라이터에서 한 레코드의 운명은 그 레코드가 속한 `(tenant=/date=/key=)` 슬롯이
언제 닫히느냐에 달려 있고, 슬롯은 **이벤트 시각**으로 닫힌다 (ADR-0005).
게다가 `sortWithinFile=true` (ADR-0004 필수)에서는 행이 close 될 때까지
**디스크가 아니라 힙**에 있다.

```java
// PartitionedParquetWriter:265-269
if (slot.buffer != null) {
    slot.buffer.add(dp);
    return;              // ParquetWriter 에 아예 넘어가지 않는다
}
```

즉 한 poll 배치 500건은 서로 다른 날짜 슬롯으로 흩어지고, 각 슬롯은 며칠 간격으로 따로 닫힌다.
**"오프셋 N 이 S3 에 갔다"가 참이어도 N−1 은 여전히 힙 안에 있을 수 있다.**

규모도 작지 않다. [W1 실측](../benchmark/p2w1-partition-closing.md)에서 워터마크 10일 창일 때
동시에 열린 파티션이 180개였다. 일당 367,200행이므로 **상시 약 440만 행(전체의 40%)이
미커밋 상태**로 남는다.

## 결정

### 1. 커밋값은 저수위선이다. "방금 올린 파일의 최대 오프셋"이 아니다

```
커밋 = min( 열린 슬롯들의 minOffset, 업로드 대기 파일들의 minOffset )
       (둘 다 비면 lastPolledOffset + 1)
```

슬롯마다 `TopicPartition` 별 `minOffset` 만 들고 있으면 된다 — 전체 오프셋 집합은 불필요하다.

이걸 "방금 올린 파일의 최대 오프셋"과 혼동하면 **(c) S3 업로드 후 커밋을 택하고도 유실이 난다.**
그게 이 ADR 에서 가장 틀리기 쉬운 지점이다.

### 2. `enable.auto.commit=false` 를 강제한다. 설정이 `true` 면 기동을 거부한다

auto-commit 은 `poll()` 안에서 `position()` 을 커밋한다. 애플리케이션이 그 레코드로 무엇을
했는지 보지 않는다. 이 파이프라인에서는 **"읽자마자 커밋"과 정확히 같다** —
힙에만 있는 배치가 커밋되고, 그 상태로 죽으면 Kafka·로컬·S3 어디에도 없다.

`PHASE2.md` 가 알려진 결함 1번에서 적은 "오프셋은 커밋됐고 hot 은 TTL 로 지워졌는데
cold 에는 없는" 상태가 그대로 만들어진다.

### 3. `auto.offset.reset=none` 으로 둔다

커밋 저수위선이 창만큼 뒤처지므로, 보존이 짧으면 커밋한 오프셋이 로그 앞머리에서 잘려나간다.
그때 기본값 `latest` 는 **로그 끝으로 점프하고 그 사이를 전부 건너뛴다 — 예외도 로그도 없이.**

W1 에서 `watermark-drop` 의 3.462% 유실을 "무손실이 cold 계층의 존재 이유"라며 기각했다.
컨슈머 기본 설정 하나가 그보다 큰 유실을 훨씬 조용하게 만드는 것을 허용할 수 없다.

기동 시 `committed(tp) < beginningOffsets(tp)` 이면 **거부하고 어느 구간이 유실됐는지 남긴다.**

### 4. 토픽 보존 ≥ 닫기 창의 2배

Redpanda 기본 보존은 7일이고 ADR-0005 의 기본 창도 7일이다. **정확히 같다.**
크래시 후 재생해야 할 구간이 보존 경계에 걸려 중복이 아니라 유실로 끝난다.

`deploy/docker-compose.dev.yml` 에 `redpanda.log_retention_ms=1209600000`(14일)을 박았다.
**보존은 닫기 창의 함수다** — 창을 늘리면 이 값도 늘려야 한다.

### 5. 라이터를 Kafka 파티션별로 분리한다

`Map<TopicPartition, PartitionedParquetWriter>`.

워터마크가 라이터당 단일 필드라(`PartitionedParquetWriter:211`) 한 라이터에 여러 Kafka
파티션이 섞이면 **랙 편차가 그대로 오염된다.** 파티션 3이 현재 시각까지 따라잡아 워터마크를
밀어올리면, 아직 10일 전을 흘리고 있는 파티션 5의 슬롯이 전부 닫힌다. 다음 레코드가 오면
재개봉이고, 스윕마다 반복되어 S3 경로 하나에 파일이 수십 개가 된다.

**지연 도착 없이도, 순전히 컨슈머 랙 편차만으로** ADR-0005 가 확정한 "재개봉 0 / 450 파일"이
무너진다. 배포·OOM·리밸런스 때마다 확정적으로 발생한다.

`HivePartitionSpecs` 도 스레드 안전하지 않으므로 라이터마다 별도 인스턴스를 준다.

### 6. 닫기 트리거를 두 축으로 한다

ADR-0005 의 이벤트 시각 워터마크에 더해, **미커밋 오프셋 span 상한**을 둔다.
넘으면 가장 오래된 슬롯부터 강제로 닫는다.

파일 품질(이벤트 시각으로 모아야 잘 압축된다)과 복구 경계(오프셋 lag 이 곧 재생량)는
**서로 다른 축**인데 지금은 축이 하나뿐이라 후자가 통제되지 않는다.

### 7. 로컬 파일의 상태를 경로로 드러낸다

```
data/archiver/inflight/<파티션경로>/....parquet.tmp    ← 쓰는 중. 언제든 폐기 가능
data/archiver/ready/<파티션경로>/....parquet           ← close 성공. 업로드 후보
```

불변식 셋:

1. `ready/` 의 모든 파일은 푸터가 있다 (`ParquetWriter.close()` 를 통과했다)
2. `inflight/` 의 모든 파일은 **무조건 폐기 가능**하다 — 그 데이터의 오프셋은 아직 커밋되지
   않았으므로 재생으로 복구된다. **1번 결정과 한 세트다.** 커밋 규칙이 틀리면 폐기가 곧 유실이 된다
3. 업로드 성공 즉시 로컬 파일을 지운다. `ready/` 에 있다는 사실 자체가 "아직 안 올라감"이다

지금은 업로드 후보 목록이 인메모리 `List<Path> closedFiles` 뿐이라
**재시작하면 무엇을 올려야 할지 알 수 없다.** 그리고 `S3ObjectStore.putTree` 는
`Files::isRegularFile` 로만 걸러서 **쓰는 중인 파일까지 올린다** — 푸터 없는 객체가
cold 에 들어가면 DuckDB 가 그 파티션을 읽을 때 질의 전체가 실패한다.
행 하나 유실이 아니라 파티션 조회 불능이다.

`inflight/` 는 반드시 업로드 루트 **바깥**에 두되 같은 파일시스템에 둔다
(`ATOMIC_MOVE` 가 성립해야 하고, `putTree` 스캔에 걸리면 안 된다).

### 8. 중복은 결정론적으로 해소되게 만든다 — **구현·검증 완료 (2026-08-16)**

재시작 중복은 **파일 단위로 깔끔하지 않다.** 크래시 전 파일과 재생본은 행 집합이 다르고
(재생은 커밋 지점부터 시작한다), 워터마크가 인메모리라 재시작 후 닫기 시점도 달라져
파일 경계가 어긋난다. 따라서 콘텐츠 해시로 멱등 PUT 하는 방법도, 옛 파일을 지우는 방법도 안 통한다.

- **파일명에 닫힌 시각을 앞에 붙인다**: `part-<closeEpochMillis>-<writerId>-<n>.parquet`.
  그래야 조회 쪽에서 "나중에 쓴 파일이 이긴다"를 결정론적으로 만들 수 있다
  (DuckDB `read_parquet(..., filename=1)` + `QUALIFY row_number() OVER (PARTITION BY device_id, ts ORDER BY filename DESC) = 1`).
  **ADR-0004 의 키 규칙을 갱신해야 한다.**
- **푸터 메타데이터에 `(topic, kafka_partition, min_offset, max_offset, writer_id, close_epoch)` 를 넣는다.**
  `ParquetStats.readFooter` 로 Java 에서 읽을 수 있으므로 ADR-0001 제약을 건드리지 않는다.

  > **실측이 이 항목의 근거를 바꿨다 (2026-08-16).** 원래는 "compaction 이 파일 단위로
  > 중복을 판단할 수 있다"는 이유로 적었는데, [`kill -9` 측정](../benchmark/p2w2-archiver.md)에서
  > **복구 정확성에 직접 필요하다**는 것이 드러났다.
  >
  > 죽은 뒤 로컬 `ready/` 에 남은 파일은 오프셋이 커밋되지 않았으면 어차피 재생된다.
  > 그걸 올리면 확정적으로 중복이 된다. 지금은 그 판단을 할 정보가 없어 "올리는 쪽"을
  > 택했고(유실을 막으려면 그래야 한다), 그 결과 중복 100% 가 나왔다.
  >
  > 메타데이터가 있으면 복구 규칙이 하나로 정해진다 —
  > `maxOffset >= 커밋 오프셋` 이면 버리고, 아니면 올린다.

**구현 결과 (2026-08-16).** 설정을 하나도 바꾸지 않고 같은 자리에서 다시 죽였다.

| | 결정 8 전 | 결정 8 후 |
|---|---|---|
| S3 객체 | 120개 / 1.3 MiB | 61개 / 0.7 MiB |
| 중복 | 367,200 (100%) | **7,200 (1.96%)** |

미커밋 상한을 낮춰 얻은 0% 와 달리 이건 슬롯을 강제로 닫지 않으므로 파일 수 대가가 없다.
[측정 상세](../benchmark/p2w2-archiver.md).

**남은 1.96% 는 이 결정으로 못 막는 다른 창이다.** 죽기 직전에 S3 로 이미 올라갔지만
오프셋은 아직 커밋되지 않은 파일 — 데이터가 `ready/` 가 아니라 S3 에 있어서 복구가 손댈 것이 없다.
창의 크기는 "마지막 커밋 이후 올린 파일 수"이고, 없애려면 업로드와 커밋이 한 트랜잭션이어야 하는데
S3 와 Kafka 사이에는 그런 것이 없다. **여기서부터는 조회 쪽 dedup 의 몫이고, 그게 동작하는 것도 확인했다.**

**복구가 "올린다"를 고르는 경우는 지금 코드에서 나오지 않는다.** `drainUploads` 가 파일마다
`업로드 → complete → 삭제` 를 끝내고 나서야 커밋하므로 `ready` 에 남은 파일의 오프셋은
항상 저수위선 뒤에 있다. 그렇다고 "무조건 버린다"로 짜면 그 결론이 `drainUploads` 의 순서에
의존하게 되고, 업로드를 병렬화하거나 커밋 지점을 옮기는 순간 조용히 깨진다 —
**그때 깨지는 방식이 유실이다.** 푸터에 좌표가 있으면 순서 논증에 기대지 않는다.

## 대가

- **W2 의 범위가 커졌다.** 배선이 아니라 상태 기계를 만드는 일이다
- **조회 쪽에 dedup 이 상시 걸린다.** ADR-0004 가 정렬로 얻은 전송 −52% 위에 얹힌다.
  지금 벤치의 쿼리 하네스는 dedup 없이 잰 숫자이므로 W2 이후 다시 재야 한다
- **커밋 저수위선이 창에 묶인다.** 7일 창이면 재생 구간이 최대 7일이다.
  근본 해법은 슬롯 버퍼를 로컬 스풀에 append+fsync 하고 그 시점에 커밋하는 것인데,
  쓰기 경로가 하나 더 생기는 결정이라 Phase 3 에서 판단한다

## 위협 모델

**프로세스 죽음(SIGKILL, OOM, 컨테이너 재기동)까지 방어한다. 커널 패닉·전원 차단은 방어하지 않는다.**

`ATOMIC_MOVE` 는 이름의 원자성만 보장하고 데이터 블록을 flush 하지 않는다.
페이지 캐시가 살아 있는 프로세스 죽음에서는 무해하지만, 전원이 나가면
**이름은 있고 내용은 쓰레기**인 파일이 생겨 불변식 1이 거짓이 된다.
방어하려면 `close()` → `FileChannel.force(true)` → `ATOMIC_MOVE` → 부모 디렉터리 fsync 순서가 필요하다.
로컬 프로젝트라 지금은 방어하지 않되, **그 선택을 여기 적어둔다.**

## 남은 질문

- ~~미커밋 오프셋 span 상한의 구체적 값~~ → [쟀다](../benchmark/p2w2-archiver.md).
  36만 건 1일치에서 2,000,000 은 한 번도 발동하지 않고, 50,000 은 중복을 0으로 만드는 대신
  파일이 12.5% 늘었다. **다만 결정 8 을 구현한 뒤로는 상한을 낮추지 않아도 중복이 1.96% 라**
  이 축의 압력이 크게 줄었다. 실운영 값은 랙 분포를 봐야 정해진다
- 리밸런스 시 `onPartitionsRevoked` 안에서 flush → upload → commitSync 를 동기로 끝내야 하는데,
  슬롯이 많으면 `max.poll.interval.ms` 를 넘길 수 있다. 그 임계를 재지 않았다
- cold↔cold 중복에서 같은 `(device, ts)` 인데 값이 다를 때의 규칙.
  "나중 파일이 이긴다"면 결국 "재생본이 이긴다"인데 그게 의도인지 명시해야 한다.
  구현은 됐지만 **값이 갈리는 데이터로 재보지 않았다** — 생성기가 결정론적이라 이 하네스에서는 안 생긴다
- dedup 질의의 비용. "조회 쪽에 상시 걸린다"를 대가로 적어놓고 아직 재지 않았다.
  [W4 벤치](../benchmark/w4-duckdb-baseline.md)를 dedup 을 켠 채로 다시 돌려야 한다
