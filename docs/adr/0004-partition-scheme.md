# ADR-0004 — 파티션 스킴

- 상태: 채택
- 일자: 2026-08-11
- 관련: W5~W6, [벤치마크](../benchmark/w5-partition-schemes.md), [ADR-0002](0002-value-layout.md)

## 맥락

cold 계층의 S3 객체 키를 어떤 규칙으로 만들 것인가. 계획서는 세 후보를 두고
"경로에 무엇을 넣을지"를 변수로 삼았다.

측정해보니 **변수가 하나가 아니었다.** 결과에 영향을 준 축이 넷이고, 그중 계획서가
예상한 것은 하나뿐이었다.

| 축 | 계획서 | 실제 영향 |
|---|---|---|
| 스킴 (경로 구성) | 유일한 변수 | 프루닝과 지연을 **정반대 방향**으로 움직임 |
| 시간 granularity | 스킴에 딸린 것 | 순수 손해. 별개 축이어야 함 |
| 파일 내 정렬 | 부수 변수 | 전송 바이트 −52% |
| Parquet 라이터 버전 | 없음 | 정렬의 손익을 **뒤집음** |

## 결정

### 1. 기본 경로는 `tenant=/date=/key=` 로 한다

```
s3://bucket/tenant=<uuid>/date=<YYYY-MM-DD>/key=<키>/part-N.parquet
```

계획서의 스킴 B 에서 **`profile=` 을 뺀 것**이다. 이유는 아래 "기각" 참고.

| | Q1 (디바이스 지정) | Q3 (전체 조회) | 나열 |
|---|---|---|---|
| A `date` | 2.10 MiB / 27ms | 6.50 MiB / 51ms | 6ms |
| **B `tenant/…/date`** | **0.76 MiB / 42ms** | **7.10 MiB / 80ms** | **16ms** |
| C `tenant/device/date` | 0.08 MiB / **1,171ms** | 15.80 MiB / 1,329ms | 540ms |

B 는 어느 질의에서도 최선이 아니지만 **어느 질의에서도 재앙이 아니다.**
A 는 넓은 질의에 좋고 좁은 질의에 3배 손해, C 는 좁은 질의에 26배 이득이지만
지연이 43배, 넓은 질의는 바이트로도 2.4배 손해다.

테넌트 분리는 성능과 무관하게도 필요하다 — 테넌트별 수명주기 정책, 삭제, 접근 제어가
경로 하나로 해결된다.

### 2. 시간 granularity 는 `date` 로 한다. `hour` 는 쓰지 않는다

| | 파일 수 | Q1 전송 | Q1 p50 |
|---|---|---|---|
| `date` | 90 | 0.76 MiB | 42ms |
| `date/hour` | 2,160 | 0.84 MiB | 1,215ms |

바이트도 늘고 지연은 29배 늘어난다. 질의가 시 단위로 좁혀지지 않는 한 얻는 것이 없다.
[W3](../benchmark/w3-partition-granularity.md)에서 크기가 2.83배 커진다는 결론이 났고,
쿼리 쪽에서도 같은 방향이다.

**granularity 는 스킴과 독립적인 축으로 관리한다.** 데이터 밀도가 지금의 24배가 되면
(디바이스 증가 등) 그때 다시 잰다.

### 3. 파일 안에서 `(device_id, ts)` 로 정렬하고 **Parquet v2 로 쓴다**

이 둘은 한 덩어리다. 따로 하면 손해다.

| | 저장 크기 | Q1 전송 | 행 그룹 프루닝 |
|---|---|---|---|
| 도착 순서 + v1 (현행) | 43.0 MiB | 2.10 MiB | 0% |
| 정렬 + v1 | 66.8 MiB (**+55%**) | 1.00 MiB | 97.7% |
| **정렬 + v2** | **37.9 MiB (−12%)** | **0.97 MiB** | **97.7%** |

정렬만 켜면 `ts` 가 행 그룹 안에서 고유해져 딕셔너리가 `PLAIN`(8바이트/행)으로 폴백하고
용량이 1.55배로 뛴다. v2 의 `DELTA_BINARY_PACKED` 가 그 손해를 없앤다
(`ts` 압축 후 210K → 10K).

라이터는 `ParquetWriter.DEFAULT_WRITER_VERSION`(= `PARQUET_1_0`)을 쓰고 있었다.
**기본값을 `PARQUET_2_0` 으로 바꾼다.**

## 기각

### 스킴 C (`tenant/device/date`) — 지금은 기각, 조건부 재검토

디바이스 지정 질의에서 전송 바이트가 26배 적다. 프루닝만 보면 압도적이다.
그런데 p50 이 1,171ms 로 43배 느리고, 그중 540ms 가 객체 나열이다.
1,530개(전체 7,650개) 객체를 나열하는 비용이 프루닝 이득을 통째로 삼킨다.
넓은 질의에서는 바이트로도 2.4배 손해다.

**재검토 조건: 매니페스트 기반 카탈로그를 도입할 때.**
Iceberg / Delta / Glue 는 파일 목록을 메타데이터로 들고 있어 LIST 를 하지 않는다.
그러면 540ms 가 사라지고 "26배 적은 바이트"만 남아 **C 가 최선이 된다.**
즉 이 기각은 스킴의 문제가 아니라 **카탈로그 부재의 문제**다. 그 사실을 기록해둔다.

### `profile=` 계층 — 기각

계획서의 스킴 B 에 있었으나 뺀다. **프루닝에 아무 기여도 하지 않기 때문이다.**

Parquet 파일 안에 같은 이름의 `profile` 열이 있어(ADR-0002 의 스키마) DuckDB 가
파일 열을 쓰고 경로 파티션을 버린다. 컬럼 목록을 조회하면 스킴 B 는 `tenant` 만
추가로 노출하고 `profile` 은 하나뿐이다. W4 의 `EXPLAIN` 에서 File Filters 에
`date` 와 `tenant` 만 잡히고 `profile` 이 없던 것도 이 때문이다.

경로만 한 단계 길어지고 이득은 0이므로 뺀다.

> **일반화**: 파티션 열과 파일 내 열의 이름이 겹치면 파티션 쪽이 죽는다.
> Hive/Iceberg 가 파티션 열을 파일에 중복 저장하지 않는 이유다.
> `tenant=` 는 파일 열 이름이 `tenant_id` 라 겹치지 않아 살아남았다 — **운이었다.**
> Phase 2 에서 스키마를 손대면 이 규칙을 명시적으로 지킬 것.

## 결과

**좋은 점**

- 좁은 질의(0.76 MiB / 42ms)와 넓은 질의(7.10 MiB / 80ms) 모두에서 극단을 피한다
- 정렬 + v2 로 저장 12% 감소, 전송 52% 감소를 동시에 얻는다
- 테넌트 경계가 경로에 있어 수명주기·삭제·접근 제어가 단순해진다

**대가**

- 디바이스 지정 질의에서 C 대비 9.5배 많은 바이트를 읽는다 (0.76 vs 0.08 MiB).
  카탈로그가 생기면 이 선택을 다시 해야 한다
- 정렬 때문에 파티션의 행을 메모리에 모았다가 닫을 때 쓴다.
  ts 오름차순 생성이라 동시 버퍼가 하루치로 제한되지만, 무한 스트림에서는
  파티션이 닫히는 시점을 별도로 관리해야 한다 (Phase 2 `archiver`)
- **크기 기반 롤링이 정렬 모드에서 동작하지 않는다.** 파일 크기를 미리 알 수 없기 때문이다.
  현재 규모에서는 롤오버가 0이라 무해하지만, 데이터가 커지면 행 수 기반 롤링이 필요하다

## 측정 조건의 한계

**행 그룹 64 KiB 는 인위적이다.** 운영은 128 MB 를 쓴다. 이 데이터셋의 파일이 10~500 KiB 라
현실적인 행 그룹을 쓰면 파일당 행 그룹이 1개가 되어 정렬 축을 잴 수 없다.
정렬의 이득(전송 −52%)은 **파일당 행 그룹이 여럿일 때만** 성립한다 —
파일이 충분히 커지거나 행 그룹을 작게 잡아야 한다.

**나열 비용이 지배하는 것은 이 규모의 성질이다.** 파일이 100 MB 급이면 바이트가 지배하고
스킴 순위가 뒤집힐 수 있다. 위 "재검토 조건"과 같은 이야기다.

**MinIO 루프백이고 동시성이 없다.** 실 S3 는 LIST 가 더 비싸 나열의 비중이 커진다 (W8).
