# 파티션을 잘 나눴더니 쿼리가 43배 느려졌다

시계열을 S3 에 Parquet 으로 내리면서 파티션 경로를 어떻게 자를지 정해야 했다.
후보는 셋이었고, 셋 다 만들어서 같은 쿼리를 돌렸다.

**스캔 바이트를 26배 줄인 스킴이 지연은 43배 느렸다.** 그게 이 글이다.

> 합성 데이터로 돌린 개인 프로젝트다. 회사 인프라나 실제 운영 데이터는 쓰지 않았다.
> 코드와 원측정치는 [ts-tiering](https://github.com/cafe-jun/ts-tiering) 에 있다.
> 이전 글: **Parquet 압축률 338배가 11.5배가 되기까지** — 분모 이야기
> (발행 후 티스토리 URL 로 링크할 것)

## 후보 셋

30일치 1,101만 행(테넌트 3개, 디바이스 51대, 키 5종, 60초 주기)을 세 경로 규칙으로 각각 적재했다.

```
A   date=2026-01-15/key=temperature/part-0.parquet
B   tenant=<uuid>/profile=industrial-sensor/date=2026-01-15/key=temperature/part-0.parquet
C   tenant=<uuid>/device=<uuid>/date=2026-01-15/key=temperature/part-0.parquet
```

쿼리는 셋이다. Q1 단일 디바이스 7일(좁게), Q2 단일 디바이스 전 기간 일평균(길게),
Q3 프로파일 전체 평균(넓게).

측정은 DuckDB 로 했고, 두 가지를 잰다.

- `EXPLAIN ANALYZE` 의 `Scanning Files: X/Y` — 파티션 프루닝이 실제로 걸렸는가
- `HTTPFS HTTP Stats` 의 `in: N bytes` — 실제로 S3 에서 끌어온 바이트

두 번째는 **연결을 매번 새로 열어야** 잡힌다. DuckDB 는 Parquet 푸터와 HTTP 응답을
연결 단위로 캐시해서, 재사용하면 전부 0 으로 나온다.

## 프루닝은 완벽하게 걸렸다

Q1(단일 디바이스 / 7일) 결과다.

| 스킴 | 스캔 파일 | 전송 | p50 |
|---|---|---|---|
| A `date` | 7 / 30 | 2.10 MiB | **27ms** |
| B `tenant/profile/date` | 7 / 90 | 0.76 MiB | 42ms |
| C `tenant/device/date` | **7 / 1,530** | **0.08 MiB** | **1,171ms** |

C 는 1,530개 파일 중 7개만 열었다. 디바이스를 경로에 넣었으니 당연하다.
전송 바이트는 A 의 **26분의 1**이다. 프루닝만 보면 압승이다.

그런데 **43배 느리다.**

## 원인은 나열이다

같은 표에 한 열을 더한다.

| 스킴 | 전송 | p50 | 그중 glob 나열 |
|---|---|---|---|
| A | 2.10 MiB | 27ms | 6ms |
| B | 0.76 MiB | 42ms | 16ms |
| C | 0.08 MiB | 1,171ms | **540ms** |

`s3://.../**/key=temperature/*.parquet` 를 풀려면 프리픽스 트리 전체를 LIST 해야 한다.
**프루닝은 그 목록이 나온 다음에야 적용된다.** 파일을 아무리 적게 읽어도
1,530개를 나열하는 비용은 그대로 낸다.

비용이 붙는 대상이 바이트가 아니라 **경로 개수**다. C 의 Q1 은 0.08 MiB 만 전송하는데
1,171ms 가 걸린다. 그중 540ms 가 순수 나열이고, 나머지도 대부분 1,530개 경로를
훑고 파티션 값을 파싱하는 데 든다. 정작 데이터를 읽는 몫은 거의 보이지 않는다.

같은 일이 쓰는 쪽에서도 벌어진다. C 를 S3 에 올리는 데 27.2초가 걸렸는데
A 는 1.7초였다. 총 용량은 74 MiB 대 43 MiB 로 1.7배 차이인데 업로드는 16배다.
객체가 7,650개냐 150개냐의 차이다.

## 넓은 질의에서는 바이트로도 최악이다

Q3(프로파일 전체)를 보면 C 의 문제가 더 분명해진다.

| 스킴 | 스캔 파일 | 전송 |
|---|---|---|
| A | 30 / 30 | **6.50 MiB** |
| B | 90 / 90 | 7.10 MiB |
| C | 1,530 / 1,530 | **15.80 MiB** |

전부 읽어야 하는 질의라 프루닝의 이득이 없고, 파일마다 붙는 푸터·딕셔너리 페이지
오버헤드만 남는다. C 의 평균 파일이 9.9 KiB 라 그 오버헤드가 데이터를 압도한다.

정리하면 C 의 이점은 **디바이스를 지정하는 질의에만** 있고, 그 외에는 용량·지연 모두 손해다.

## 시 단위로 쪼개는 건 그냥 손해였다

계획 단계에서는 `date=/hour=` 를 쓰려 했다. 재봤다.

| | 파일 수 | Q1 전송 | Q1 p50 |
|---|---|---|---|
| `date` | 90 | 0.76 MiB | 42ms |
| `date/hour` | 2,160 | 0.84 MiB | **1,215ms** |

바이트도 늘고 지연은 29배다. 질의가 시 단위로 좁혀지지 않는 한 hour 파티션은
프루닝에 기여하지 못하면서 파일만 24배로 쪼갠다.

**파티션 축을 하나 늘리는 건 공짜가 아니다.** 그 축으로 거르는 질의가 실제로 있을 때만 이득이다.

## 여기서 예상 못 한 게 나왔다

파일 안에서 `(device_id, ts)` 로 정렬하면 행 그룹의 `device_id` min/max 가 좁아져
행 그룹 단위 프루닝이 걸린다. 실제로 걸렸다 — 건너뛴 행 그룹 0% → **97.7%**,
전송 바이트 **−52%**.

그런데 **저장 용량이 43.0 → 66.8 MiB, 1.55배로 뛰었다.**

열별로 뜯어보니 범인은 `ts` 하나였다.

| | `ts` 압축 전 → 후 | 인코딩 |
|---|---|---|
| 도착 순서 | 21K → 20K | `PLAIN_DICTIONARY` |
| 정렬 | 577K → **210K** | **`PLAIN`** |

도착 순서(생성기가 ts 를 바깥 루프로 돈다)에서는 한 행 그룹 안에 고유 ts 가 11개뿐이다.
같은 시각의 51개 디바이스가 연달아 오기 때문이다. 딕셔너리가 거의 공짜로 먹는다.

정렬하면 한 행 그룹이 한 디바이스의 연속된 566개 타임스탬프가 된다. 전부 고유값이라
딕셔너리가 이득을 잃고 **`PLAIN`(8바이트/행)으로 폴백한다.**
`device_id` 에서 아낀 35K 보다 `ts` 에서 잃은 190K 가 훨씬 컸다.

## 라이브러리 기본값이 범인이었다

오름차순 정수는 델타 인코딩에 이상적이다. Parquet 에는 `DELTA_BINARY_PACKED` 가 있다.
**단, Parquet v2 부터다.** 그리고 `parquet-java` 의 `DEFAULT_WRITER_VERSION` 은 `PARQUET_1_0` 이다.

v2 로 바꿔서 다시 쟀다.

| | 도착 순서 | 정렬 |
|---|---|---|
| v1 | 43.0 MiB | 66.8 MiB (**+55%**) |
| **v2** | 43.4 MiB | **37.9 MiB (−12%)** |

`ts` 는 압축 후 210K → **10K** 가 됐다.

결론이 완전히 뒤집힌다. v1 에서 정렬은 "전송 절반을 사려고 저장 1.55배를 내는" 교환이었는데,
v2 에서는 **저장도 줄고 전송도 줄어드는 순수 이득**이다.

기본값 하나가 최적화의 이점을 통째로 가리고 있었다.

## 그리고 아무 일도 안 하던 디렉터리

스킴 B 의 `profile=` 계층은 프루닝에 **아무 기여도 하지 않았다.**

DuckDB 에 컬럼 목록을 물어보면 답이 나온다. 스킴 B 는 `tenant` 만 추가로 노출하고
`profile` 은 하나뿐이다. Parquet 파일 안에 이미 `profile` 열이 있어서
**파일 열이 경로 파티션을 가려버린다.**

경로만 한 단계 길어지고 얻는 건 없다. Hive 나 Iceberg 가 파티션 열을 파일에
중복 저장하지 않는 이유가 이것이었다.

`tenant=` 가 살아남은 건 파일 열 이름이 `tenant_id` 라 우연히 안 겹쳤기 때문이다. 운이었다.

## 무엇을 골랐나

`tenant=/date=/key=` + `(device_id, ts)` 정렬 + **Parquet v2**.

원래 후보였던 스킴 B 대비 저장 −13%, 좁은 질의 전송 −45%.
어느 질의에서도 최선은 아니지만 어느 질의에서도 재앙이 아니다.

**스킴 C 는 조건부 기각이다.** 카탈로그가 있으면 이야기가 달라지는데,
그 조건이 생각보다 까다로웠다 — 아래 "덧"에서 실제로 재봤다.

파티션 설계를 아무리 잘해도, 파일 목록을 매번 나열해야 하는 구조에서는
그 이득을 회수하지 못한다. 그게 이번 측정에서 가장 오래 남을 교훈인 것 같다.

## 조건과 한계

- **행 그룹을 64 KiB 로 낮춰서 쟀다.** 운영은 128 MB 를 쓴다. 이 데이터셋의 파일이
  10~500 KiB 라 현실적인 행 그룹을 쓰면 파일당 행 그룹이 1개가 되고, 그러면 정렬 순서
  실험 자체가 불가능하다. **정렬의 이득은 파일당 행 그룹이 여럿일 때만 성립한다.**
- **나열이 지배하는 것은 이 규모의 성질이다.** 파일이 100 MB 급이면 바이트가 지배하고
  순위가 뒤집힐 수 있다
- 로컬 MinIO 루프백이다. 실 S3 에서 어떻게 달라지는지는 확인하지 못했다
- 단일 프로세스이고 동시성은 재지 않았다
- 채택안의 Q3 전송이 7% 늘어난 건 설명하지 못했다. 전체 용량은 13% 작은데 넓은 질의만
  더 읽는다. 페이지 읽기 패턴 차이로 보이나 추적하지 않았다

## 덧: 카탈로그를 흉내내 봤다

"카탈로그가 있으면 C 가 최선"이라고 써놓고 보니 그건 측정이 아니라 주장이었다.
그런데 DuckDB 는 glob 대신 파일 경로 목록을 직접 받는다. 목록을 미리 만들어 넘기면
S3 를 나열하지 않으므로, 그게 카탈로그가 하는 일이다. AWS 없이 확인할 수 있었다.

| Q1 p50 | A | B | C |
|---|---|---|---|
| glob | 28ms | 48ms | 1,092ms |
| 목록만 전달 | 21ms | **15ms** | 84ms |
| 목록을 걸러서 전달 | 21ms | 10ms | **6ms** |

**나열을 없애는 것만으로는 부족했다.** C 는 84ms 로 13배 빨라졌지만 B(15ms)보다
여전히 5.6배 느리다. 경로 1,530개를 훑는 비용이 남는다.
카탈로그가 파티션 통계로 걸러서 7개만 넘겨야 **6ms**, 그때 처음으로 최선이 된다.

내가 처음에 지목한 메커니즘("나열이 사라진다")은 틀렸고 결론("C 가 최선")은 맞았다.
조건이 더 강했던 것이다 — 파일 목록을 주는 카탈로그가 아니라
**파티션 통계로 걸러주는** 카탈로그여야 한다.

단, 넓은 질의는 카탈로그로도 해소되지 않는다. Q3 에서 C 는 1,866ms 로 A(59ms)의 31배이고
모드를 바꿀수록 오히려 나빠진다. 파일 7,650개라는 형상 자체가 비용이기 때문이다.
