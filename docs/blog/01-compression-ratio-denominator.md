# Parquet 압축률 338배가 11.5배가 되기까지

IoT 시계열을 S3 에 Parquet 으로 내리는 사이드 프로젝트를 하고 있다.
첫 측정에서 **338배**가 나왔다. 그대로 발표했으면 거짓말을 할 뻔했다.

세 번에 걸쳐 숫자가 내려왔고, 내려온 이유가 각각 다르다. 그 과정이 이 글이다.

> 합성 데이터로 돌린 개인 프로젝트다. 회사 인프라나 실제 운영 데이터는 쓰지 않았다.
> 코드와 원측정치는 [ts-tiering](https://github.com/cafe-jun/ts-tiering) 에 있다.

## 1차: 338배

ThingsBoard 의 `ts_kv` 형태를 모사한 합성 텔레메트리 1천만 건을 만들었다.
온도는 완만한 sine + 노이즈, 가동상태는 대부분 불변, 에러코드는 "OK" 가 98%.
평평한 난수를 쓰면 압축률 측정이 무의미해지므로 값 분포에 시간을 썼다.

| | 크기 |
|---|---|
| NDJSON | 1,966,190,528 B (1,875 MiB) |
| Parquet + ZSTD | 5,817,227 B (5.5 MiB) |

**338배.** 기분이 좋았다.

그런데 열별 내역을 보다가 이상한 걸 발견했다. `ts` 컬럼이 압축 후 **37 KB** 밖에 안 됐다.
천만 행의 타임스탬프가 37 KB 라고?

기본 설정이 디바이스 600대 × 10초 주기였다. 1천만 건이면 **9시간**밖에 커버하지 못한다.
`ts` 의 고유값이 3,240개뿐이라 딕셔너리 인코딩이 비현실적으로 잘 먹은 것이다.
실제 운영은 1년치를 담는데, 그러면 고유 타임스탬프가 수십만 개가 된다.

즉 338배는 **데이터셋이 너무 짧아서 나온 숫자**였다.

## 2차: 190배

커버 기간을 1년으로 맞췄다. 디바이스 51대 × 60초 주기 × 365일 = 134,028,000 건.

| | 크기 | 건당 |
|---|---|---|
| NDJSON | 26,375,747,843 B (24.6 GiB) | 196.8 B |
| Parquet + ZSTD | 138,414,594 B (132.0 MiB) | 1.03 B |

**190배.** 커버 기간을 현실화했더니 338배가 190배가 됐다.

여기까지는 측정의 문제였다. 그런데 더 근본적인 문제가 남아 있었다.

## 분모가 틀렸다

**NDJSON 을 분모로 쓰는 게 정당한가?**

NDJSON 은 필드명(`"tenantId"`, `"deviceId"`, `"value"`…)과 UUID 36자를 **매 행 텍스트로 반복**한다.
아무도 시계열을 이렇게 저장하지 않는다. 우리 데이터는 Cassandra 에 있다.

회사를 설득할 때 필요한 문장은 "JSON 보다 190배 작습니다"가 아니다.
**"지금 Cassandra 가 먹고 있는 디스크의 몇 분의 일입니까"**다.

## 3차: 11.5배

해석적으로 추정할 수도 있었다 — 행 오버헤드 × 행 수. 하지만 셀 헤더, 타임스탬프 델타,
LZ4 청크 경계가 얽혀서 2배쯤 틀리기 쉽다. 그러면 결론을 인용할 수 없다.

그래서 로컬에 Cassandra 를 띄우고 ThingsBoard 의 `ts_kv_cf` 스키마를 그대로 세웠다.

```sql
CREATE TABLE thingsboard.ts_kv_cf (
    entity_type text, entity_id uuid, key text, partition bigint, ts bigint,
    bool_v boolean, str_v text, long_v bigint, dbl_v double, json_v text,
    PRIMARY KEY ((entity_type, entity_id, key, partition), ts)
);
```

충실도가 곧 숫자의 신뢰도라 두 가지를 지켰다.

- **파티션 규칙은 TB 기본값**(`TS_KV_PARTITIONING=MONTHS`)을 따랐다. 파티션을 임의로 자르면
  파티션 헤더 대 행 수의 비율이 달라져 크기가 통째로 바뀐다
- **압축 설정은 건드리지 않았다.** Cassandra 기본값(LZ4)이 운영에서 쓰이는 값이다.
  여기서 손대면 분모가 내게 유리하게 왜곡된다

같은 30일치 데이터(11,016,000 행)를 세 방식으로 저장한 결과다.

| 저장 방식 | 크기 | 행당 |
|---|---|---|
| NDJSON | 2,167,232,293 B | 196.7 B |
| **Cassandra `ts_kv`** | **129,888,500 B** | **11.79 B** |
| **Parquet + ZSTD** | **11,272,888 B** | **1.02 B** |

**11.5배다.** 190배가 아니라.

## 190배는 어디로 갔나

여기가 이 글에서 제일 하고 싶은 이야기다. 190배를 분해해보면 이렇게 된다.

```text
NDJSON      →  Cassandra    16.7배    "JSON 이 뚱뚱했다"
Cassandra   →  Parquet      11.5배    Parquet 이 실제로 한 일
                            -----
              16.7 x 11.5 = 192배
```

**Cassandra 자체가 이미 NDJSON 을 16.7배 압축하고 있었다.**
그러니까 190배 중 대부분은 Parquet 의 공이 아니라 "JSON 을 안 쓰면 당연히 줄어든다"는 뜻이었다.

압축비를 발표할 때 분모를 명시하지 않으면, 사실상 **기존 시스템이 이미 하고 있던 일을
내 공으로 가져가는 것**이 된다. 338배와 11.5배는 30배 차이인데 둘 다 "같은 데이터, 같은 Parquet"에서 나왔다.

## 곁가지: 저장한 것의 67.5%가 오버헤드였던 순간

분모 문제와 별개로, 파티션 경로를 정하다가 한 번 더 걸렸다.

원래 계획은 `tenant=/profile=/date=/hour=` 였다. 그런데 대입해보니 시(hour) 파티션 하나에
들어가는 행이 **1,020행**밖에 안 됐다. 천 행짜리 Parquet 파일이면 푸터와 딕셔너리 페이지가
데이터보다 클 수도 있겠다 싶어 양쪽을 다 만들어봤다.

| granularity | 파일 수 | 평균 파일 | 총 크기 |
|---|---|---|---|
| `date/hour` | 10,800 | 2.9 KiB | 30.5 MiB |
| `date` | 450 | 24.5 KiB | **10.8 MiB** |

같은 데이터, 같은 레이아웃, 같은 코덱인데 **시 단위로 쪼갠 쪽이 2.83배 크다.**

차이가 전부 파일 수에서 오므로 파일당 고정 오버헤드를 직접 뽑을 수 있다.

```
(31,958,328 − 11,272,888) ÷ (10,800 − 450) = 1,999 bytes/file
```

파일당 약 2 KB. 시 단위 파일이 평균 2.9 KiB 였으니 **전체의 67.5%가 오버헤드**였다.
데이터가 아니라 푸터와 메타데이터를 저장하려고 S3 에 올리고 있었던 셈이다.

이건 업로드 시간에도 그대로 나타났다. 1년치 132 MiB 를 올리는 데 24.1초, 5.5 MiB/s.
루프백 치고 형편없는 수치인데 객체당으로 보면 4.4 ms 로 일정했다.
전송이 아니라 **요청 왕복 5,475번**이 걸린 시간이었다.

## 정리

- **압축비를 말할 땐 분모를 같이 말하자.** "원본 대비"의 원본이 무엇인지에 따라 30배가 왔다 갔다 한다
- **합성 데이터의 커버 기간을 확인하자.** 타임스탬프 카디널리티가 낮으면 딕셔너리가 과적합하고,
  그 이득은 운영에서 재현되지 않는다
- **분모는 추정하지 말고 재자.** 스키마를 그대로 세우고 넣어보는 데 반나절이면 된다.
  해석적 모델로 2배 틀린 숫자보다, 가정을 명시한 실측 하나가 낫다
- **파일을 잘게 쪼개는 비용은 용량과 시간 양쪽에 붙는다.** 파티션 granularity 는
  프루닝 효율만의 문제가 아니다

## 이 숫자의 한계

11.5배도 조건부다. RF=1 단일 노드에서 TTL 없이 쟀고, Cassandra 4.1 기준이며, 합성 데이터다.
운영은 보통 RF=3 이라 디스크는 3배가 되고(그 기준이면 약 34배), TTL 을 걸면 셀마다
만료 정보가 붙어 Cassandra 쪽이 더 커진다. 실제 클러스터의 hint 나 repair 잔여물도 빠져 있다.

**전부 Cassandra 쪽을 작게 만드는 방향이므로 11.5배는 하한이다.**
그래도 338배보다는 이 숫자를 들고 가겠다.
